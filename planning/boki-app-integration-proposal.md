# 簿記論アプリ 統合提案(design brief × 調査レポート)

このファイルは、以下2つを統合し、再評価した提案である。

- `planning/bookkeeping-app-design-brief.md`(このリポジトリで作成した設計メモ)
- 「簿記論アプリ立ち上げに向けた調査レポート」
  (別セッション=ローカルのClaude Codeで作成され、ユーザーから要点を
  1〜6項目としてこのセッションへ共有されたもの。原文そのものはこのセッションに
  存在しないため、共有された要点にもとづいて再評価している)

**このファイルはあくまで提案。新規リポジトリ作成・実装はまだ行っていない。**
ユーザー確認後、新規 `boki-app` プロジェクトへこの内容を持ち込むことを想定する。

---

## 1. 両者で一致している方針

- 目的は「教材をそのままデジタル問題集へ変換する」ことではなく、
  「最も効果的な簿記論の問題集を作る」こと。
- 教材は問題集ではなく教科書を使う(基礎4冊+上級4冊、計8冊)。
- 8冊を最初から処理せず、基礎コース1冊目のみで
  調査→構造分析→抽出方法検討→中間データ設計→ユーザー確認→実装・検証
  まで行い、その結果を踏まえて残り7冊にスケールする。
- 財表と異なり、簿記論では原文をそのまま構造化するだけでは目的を達成できない
  可能性がある。型・公式を統合・一般化した派生データが必要。
- 派生データは必ず元の原文(Source)への出典参照を持ち、
  根拠のない創作をしない。確信が持てないものはunknown/unresolvedとして保存する。
- 出題形式は固定しない。特に公式ドリル(言語表現+文字式)は、
  既存`ordering`(`assembledFromSource`前提)をそのまま流用できない可能性が高く、
  教材調査後に適切なモデルを設計する。
- 実装・新規リポジトリ作成にはまだ進まず、設計の確定を先に行う。

---

## 2. 矛盾・変更が必要な方針

### a. リポジトリ構成(矛盾)

- design brief: 既存のzaihyo-parserパイプラインを**同一リポジトリ内で**再利用・拡張する
- 調査レポート: 簿記論アプリは**別リポジトリ**として立ち上げ、
  リポジトリ・コードベースは独立させつつ、設計資産・アーキテクチャ・
  有用なコードはzaihyo-parserの派生として積極的に再利用する

→ **調査レポート側を採用する。**
ユーザーが直近のメッセージで「新規boki-appプロジェクト作成へ進みます」と
明言しているため、これは実質的に決定事項として扱ってよい。
design brief内の「既存パイプラインを再利用・拡張する」という記述は、
「別リポジトリだが設計資産・アーキテクチャを再利用する」という表現に
更新が必要。

### b. レイヤー数(変更)

- design brief: 原文保持レイヤー / 知識統合レイヤー の2層
- 調査レポート: Source / Derived Knowledge / Exercise の3層

→ **3層構造を採用する。**
「知識を統合すること」と「その知識をどう出題するか」は別の関心事であり、
分離しておくほうが将来の出題形式追加(原則7「問題形式を固定しない」)に強い。

### c. 学習仮説の確度の書き方(表現の変更)

- design brief: 「仕訳の型」「公式」の2つが本質、とやや言い切り気味に記述
- 調査レポート: 明確に「学習仮説」として扱い、教材調査で2分類に収まらない
  本質的な学習要素が見つかった場合は無理に押し込まず報告する、
  という検証的なスタンスを明示

→ **調査レポート側の慎重な表現を採用する。**
CLAUDE.md/SPEC.mdに書く際も「仮説」であることを明記する。

## 3. 今回のメモ(design brief)によって新たに判明した重要要件

調査レポートの要点(共有された1〜5項目)には含まれていなかった、
design brief固有の重要な内容。新リポジトリでも引き継ぐべき。

- **有償ライセンス教材の取り扱い規約**: 原本PDF・教材原文を含む
  中間/派生データは一切コミットしない。`.gitignore`で`/input/`等を除外する、
  というzaihyo-parserの運用ルール。調査レポート側には言及がないため、
  新リポジトリで明示的に再設定する必要がある。
- **基礎/上級を横断した統合の具体的な扱い**:
  複数教科書に共通して出てくる型・公式は「本質的なパターン」の裏付けとして扱い、
  上級だけに出てくるものは応用パターンとして区別する、という統合ヒューリスティックの原案。
  調査レポートも同種の課題(3節)に触れているが、design briefのほうが
  具体的な判定基準("複数書で重複=本質")まで踏み込んでいる。
- **既存出題形式ハンドラの技術的詳細**: `html-v2/js/registry.js`の
  `single_blank`/`multi_blank`/`ordering`各ハンドラの実装内容
  (`ordering`が`assembledFromSource`という「元の一文の文節復元」前提であること等)。
  調査レポートは同じ結論(流用不可の可能性)に達しているが、design briefには
  その根拠となる実装レベルの参照がある。新リポジトリで参考実装として
  読む際の具体的な参照先になる。

## 4. Zaihyo Parserから再利用すべきものの再評価

「コードベースは分離、設計資産は再利用」という方針のもとでの再評価。

**再利用すべき(設計パターン・考え方として)**
- BookStructureMaster(BSM)の「原文→構造を保持した中間データ」という設計パターン。
  ただしスキーマ自体は簿記論の教材構造(教科書の章立て等)に合わせて作り直す必要がある。
  そのまま流用するのはスキーマではなく「原文保持・出典追跡・unknown許容」という考え方。
- ExerciseViewの**レジストリパターン**
  (出題形式ごとにハンドラを1エントリ追加するだけで拡張できる設計、
  `html-v2/js/registry.js`のEVv2.registry相当)。これは簿記論のExercise層にも
  そのまま有効なアーキテクチャ。
- `src/*/validator.mjs`群にある「出典存在検証」「重複ID検証」「原文一致検証」等の
  検証パターンの考え方。Derived Knowledgeの「根拠のない知識を作らない」原則を
  機械的にチェックする仕組みとして応用できる。
- html-v2のUI基盤のうち、教材内容に依存しない共通部品
  (進捗保存`progressStore.js`、テーマ`themeStore.js`、drag&drop`dragReorder.js`、
  タップ選択順序のUIパターン等)。データ構造非依存な部分は移植候補になる。

**そのまま移植すべきではない(財表固有)**
- `csvBridge`/`confirmCsv`/`knowledgeMaster`/`knowledgeMasterExporter`など、
  財表のCSV出力・レビュー運用に特化したコード群。簿記論のDerived Knowledge統合とは
  目的が異なるため、参考程度に留める。
- BSM/ExerciseViewの具体的なフィールド定義そのもの(教材構造が違うため)。

## 5. 新しい簿記論アプリのデータフロー案

3層構造(Source / Derived Knowledge / Exercise)にもとづく案。

```
教科書PDF
   │  Parser(テキスト抽出・ページ/章構造化)
   ▼
[Source層]  … 原文保持。財表のBSM相当だが簿記論用に作り直す。
             章・単元・例題・仕訳・公式記述などを原文のまま構造化。
             要約・言い換え禁止(zaihyo-parser原則5を継承)。
   │  型・公式の抽出・統合(人力レビュー + AI補助)
   ▼
[Derived Knowledge層] … 仕訳の型・公式(言語表現/文字式)を統合・一般化。
             各項目は必ずSource層の該当箇所への出典参照(1件以上)を持つ。
             複数教科書で同一パターンが確認された場合は出典を複数保持し、
             「本質パターン」として扱う。上級のみで確認されたものは
             応用パターンとして区別するフラグを持つ。
             出典を辿れない・確信が持てないものはunknown/unresolvedとして保存し、
             無理に統合しない。
   │  出題形式ごとのビュー生成
   ▼
[Exercise層] … Derived Knowledgeを教材とする出題データ。
             仕訳の型 → 穴埋め系(single_blank/multi_blank相当を再設計)
             公式 → 言語表現/文字式のペアを扱う新モデル(要新規設計、
             既存orderingの`assembledFromSource`前提は流用しない)
             ExerciseViewのレジストリパターンを踏襲し、
             将来の新形式追加を1エントリ追加で完結できる設計にする。
   ▼
アプリ(学習UI) … html-v2相当。データに依存しない共通部品は移植候補。
```

補足: Derived Knowledge層は「1冊処理して終わり」ではなく、
新しい教科書を追加するたびに既存の型・公式と照合・統合し続ける
継続的なプロセスとして設計する(基礎/上級を跨いだ統合が前提のため)。

## 6. CLAUDE.mdに置くべき原則

新リポジトリ(boki-app)のCLAUDE.mdは、zaihyo-parserのCLAUDE.mdと同様、
**変更頻度が低い、プロジェクトの不変の考え方**を書く場所とする。

1. 目的: 教材をそのままデジタル問題集に変換するのではなく、
   最も効果的な簿記論問題集を作ること。
2. 教材を最優先する。教材が持つ構造を可能な限り保持し、
   出力フォーマットに合わせて教材を変形しない。
3. Source(原文)は失わない。要約・言い換えは禁止。
4. Derived Knowledge(型・公式)は統合・一般化してよいが、
   必ずSourceへの出典参照を持たせ、根拠のない創作をしない。
   確信が持てないものはunknown/unresolvedとして保存する。
5. 推測しない。既存の分類・形式に無理に押し込まない。
   未知の要素は報告し、unknownとして扱う。
6. 問題形式を固定しない。Exercise層はレジストリで拡張できる設計にする。
7. 教材は一度に大量投入しない。1冊単位で設計→検証→スケールする。
8. 有償ライセンス教材の取り扱い: 原本・教材原文を含む中間/派生データは
   コミットしない。

## 7. SPEC.mdに置くべきプロダクト仕様・学習仮説

SPEC.mdは、CLAUDE.mdより**変更頻度が高く、教材調査によって更新されうる**、
「現時点で分かっている仕様」を書く場所とする。

- **学習仮説(検証中であることを明記)**:
  仕訳の型の穴埋め反復 + 公式(言語表現・文字式)の並び替え反復、
  この2つの高速回転が簿記論の本質的な学習効果を生む、という仮説。
  固定仕様ではなく、教材調査を通じて検証・拡張する。
  この2分類に収まらない本質的な学習要素が見つかった場合は、
  無理に分類せず報告する。
- **データモデル仕様**: Source / Derived Knowledge / Exercise
  3層の定義(各層のフィールド、出典参照の持たせ方、
  unknown/unresolvedの扱い、基礎/上級の統合フラグ)。
- **教材スコープ**: 基礎コース4冊・上級コース4冊、計8冊。
  基礎コース1冊目から着手。
- **出題形式の初期スコープ**: 仕訳穴埋め(blank系ベース)、
  公式並び替え(新モデル、教材調査後に確定)。
- **基礎/上級統合ロジックの仕様**: 同一パターンの統合方法、
  応用パターンの区別方法(教材調査後に詳細確定)。

## 10. 教材調査後まで決めない方がよいこと

- Source層の具体的なスキーマ(教科書の章・単元・例題・仕訳・公式の
  実際の記法が分かってから設計する)
- Derived Knowledgeの具体的な抽出アルゴリズム・統合ルールの詳細
  (実データを見てから)
- 公式ドリル用のExercise/Presentationモデルの具体的なUI・データ構造
  (orderingを流用しないとは決めたが、代替案の具体形は教材調査後)
- 基礎/上級横断統合の具体的な照合方法(表記ゆれの扱い等)
- Zaihyo Parserのコードをどう技術的に共有するか
  (npmパッケージ化、コピーして育てる、参考実装として見るだけ、等の実装判断)
- 8冊全体にスケールする際のディレクトリ構成・命名規則

## Single Source of Truth(SSOT)の提案

| ファイル | 役割 | 変更頻度 | 内容 |
|---|---|---|---|
| `CLAUDE.md` | 不変に近い原則 | 低 | なぜ・何を優先するか(本提案6節) |
| `SPEC.md` | 現時点の仕様・学習仮説 | 中 | データモデル・スコープ・仮説(本提案7節) |
| `TASK.md` | 直近の実行タスク | 高 | チェックリスト(本提案8節) |
| `planning/`(設計メモ) | 意思決定の経緯・議事録 | 追記のみ | なぜその結論に至ったか |

**重複を避けるルール**
- 同じ情報を複数ファイルに書かない。CLAUDE.mdに書いた原則を
  SPEC.mdで繰り返し説明せず、必要なら「原則はCLAUDE.md参照」とリンクするだけにする。
- 矛盾が生じた場合は CLAUDE.md > SPEC.md > TASK.md の順を「今何が正か」の
  優先順位とし、planningは経緯説明に徹する(planningの記述が正にはならない)。
- 現在の`planning/bookkeeping-app-design-brief.md`および本ファイルは、
  新リポジトリ移行後は「経緯ログ」としてそのまま残し、
  正式な仕様はSPEC.mdへ切り出す。design brief内の「今後変わりうる仕様的記述」は
  SPEC.mdへ移し、design briefには「なぜその仕様に至ったか」の説明だけ残す。
