## 1. 現在地から「解ける」までの依存関係

### 1-1. 工程の依存チェーン(何が何をブロックするか)

```
[a] Parser最小プロトタイプ(確定Source 1件の生成、2節で詳述)
      ↓ ブロック: これが無いと後続すべてが「架空データ」でしか試せない
[b] Source候補一覧レポートの試作出力(概念スキーマの妥当性確認)
      ↓ ブロック: [8]候補確定フェーズの入力形式が決まらないと設計できない
      ※ ただし3節で選ぶ最初のケースは候補ゼロ件で通るため、[a]の直後に
        並行して進められる(3節参照)
[c] Derived Knowledge候補の半自動生成(1件、calculation_formula)
      ↓ ブロック: [a]の確定Sourceが無いと出典参照(sourceRefs)を持てない
[d1] 開発用確認UI(閲覧のみ、新設・5-1節)
      ↓ [a]の出力だけで着手でき、[c]の完了で表示内容が完成する
      ↓ ブロック: [d2](操作の追加)の土台になる
[d2] [d1]への承認/修正/除外操作の追加(5-2節)
      ↓ ブロック: [c]の候補が無いと承認対象が無い
[e] 承認済みKnowledge 1件の確定
      ↓ ブロック: [d2]で承認操作が動かないと生成されない
[f] Exercise生成(1問、並び替え形式)
      ↓ ブロック: [e]の承認済みKnowledgeが無いと出題データが作れない
[g] 学習UI(最小)
      ↓ ブロック: [f]のExerciseデータが無いと表示・採点ができない
```

**[a]→[c]→[d2]→[e]→[f]→[g]が直列のクリティカルパスである。** [b](候補一覧
レポート)は、3節で選ぶ最初のケースに限れば候補が発生しないため、クリティカル
パス上には乗らない。ただし候補提示方針の全体設計を裏付けるため、[a]と並行して
空(0件)でも構造だけ正しいレポートを一度出力しておく価値はある(2節)。

**(今回の修正で追加)** [d1](開発用確認UI)は、クリティカルパス上の新しい
成果物ではなく、**[a]〜[c]で既に生成されている実データを可視化するだけの
薄いレイヤー**である。[a]の出力だけでも(Knowledge候補が無い状態でも)
「PDF上の元データ→抽出結果→sourceFaithful→確定Source」までは表示でき、
[c]完了後に「Derived Knowledge候補」の表示を追加すればよい。これにより、
[c]を待たずに[a]完了時点で最初の確認体験を得られる(8節・10節で詳述)。

### 1-2. 「何を先に作らないと次へ進めないか」の判断基準

- **後工程の入力形式を規定するものは先に作る**: Source層のフィールド構造
  (`extractionRaw`/`sourceFaithful`/`parsed`/`diag`、`location`)は
  Derived Knowledgeの`sourceRefs`が参照する対象そのものであるため、
  最初のケース分だけでも実データとして先に存在させる必要がある。
- **後工程が無くても検証できるものは後回しにできる**: 候補確定フェーズの
  UIや汎用Parserの検出精度向上は、最初の1ケースが候補ゼロ件で通る限り
  クリティカルパスに影響しない。

### 1-3. どこは仮実装でよいか / どこは正式設計に従う必要があるか

| 領域 | 判断 | 理由 |
|---|---|---|
| Source層のフィールド構造(4概念モデル・`location`) | **正式設計に従う** | `source_derived_knowledge_design_proposal.md`12節で「承認済み(最終形)」。後から変えると[c]以降が全て作り直しになる |
| `sourceRefs.role`・`evidence.byRole`・3軸状態モデル | **正式設計に従う** | 同じく承認済み(最終形)。Derived Knowledgeの根幹 |
| `structure.tokens`(term/operator/fraction/group/power) | **正式設計に従う** | 承認済み(最終形)。Exercise(並び替え)の入力データそのもの |
| Source候補一覧レポートの正式スキーマ | **仮実装でよい** | 概念設計のみ確定(3-8節)。最初のケースでは候補ゼロ件のため、構造の形だけ正しければ十分 |
| [8]候補確定フェーズのUI | **仮実装でよい(最初のケースでは不要)** | 3節で選ぶ最初のケースは候補が発生しない。第2ケース(定額法の複数適用)で初めて必要になる |
| gateChecks | **仮実装でよい** | 18候補中、最初のケースに関係する数件(親子なしなので構造チェックのみ)に絞ってよい。全項目実装は後回し |
| `diag`の正式スキーマ | **仮実装でよい** | フィールド名・型は未確定(10節)。最初のケースで実際に使うキー(`extraction.status`・`extraction.artifacts`・`faithfulReconstruction`)だけ最小実装すればよい |
| レビューUI | **仮実装でよい(かつ段階的に育てる)** | 5節のとおり、まず[a]完了直後に閲覧専用の開発用確認UIを置き、[c]完了後に承認/修正/除外の操作を同じ画面へ追加する。デザイン・操作性の作り込みは後回し |
| Exercise生成ロジック | **仮実装でよい** | 1件を手動トリガーで生成できれば足りる。バッチ化・自動化は後回し |
| 学習UI | **仮実装でよい** | 1問を見る→答える→正誤を見るの最小機能のみ。デザインは最小限 |

## 2. 最小Parserプロトタイプのスコープ

### 2-1. ユーザー提示の想定([1]〜[4]+候補一覧レポート)の評価

提示された範囲(Extraction→StructureNode→Block Detection→確定/候補振り分け→
候補一覧レポート出力)は、**Parserパイプライン全体の責務としては正しい最小
範囲である。** ただし、3節で選ぶ最初のケース(定額法の定義式ブロック)に
限って言えば、これだけでは後工程(Derived Knowledge生成)に渡せるデータが
完成しない。

### 2-2. Faithful Restoration([5])を最小限含める必要がある理由

`planning/parser_source_granularity_validation.md`ケース5で確認されているとおり、
定額法の定義式ブロック(テーマ8-2)は**`pdftotext`による分数の分子/分母の分離
(`fraction_split`)という既知の抽出崩れの実例そのもの**である。この崩れを
`sourceFaithful`へ書き戻さない限り、Derived Knowledgeの`rawFormula`(教材上の
忠実な式表現。必須フィールド、5-2節)を正しく作れない。

したがって、最小Parserプロトタイプには**[5] Faithful Restorationを、この
1ケースの`fraction_split`補正に限定して含める**。全既知パターン
(`exponent_split`・`column_order_shift`等)の自動化までは不要で、このケース
1件分を`method: "human_reviewed"`(6-1節の運用方針どおり)で書き戻せれば足りる。

### 2-3. Parsing([6])は最小プロトタイプでは不要

[6] Parsingは`blockKind`ごとの`parsed`構造を生成する段階だが、`parsed`の
正式構造が確定しているのは`table`のみ(3節)であり、`calculation_formula`
(Source側のblockKindでは`formula_termbased`)には`parsed`の構造化は定義されて
いない。3節で選ぶケースの`structure.tokens`は**Source層の`parsed`ではなく
Derived Knowledge層の`content.structure`**(5-2節)であり、Source→Derived
Knowledge変換段階([c])で生成するものである。よって、最小Parserプロトタイプの
範囲には[6]を含めない。

### 2-4. 確定した最小Parserプロトタイプのスコープ

```
[1] Extraction
[2] Structure Recognition(テーマ8-2までの階層検出)
[3] Block Detection(用語ベース計算式パターン検出器)
[4] Source Segmentation
     → このケースは既にトップレベル(F3で確定)のため、候補化されず
       即座に確定Sourceとなる(3-3節で詳述)
[5] Faithful Restoration(このケース1件の fraction_split 補正のみ)
[7] Validation / Diagnostics
     → 該当ケースに関係するgateChecksのみ最小実装
     → Source候補一覧レポートは「候補0件」の構造として出力(スキーマの
       形の検証のみが目的。3節で第2ケースに進む際に本格的に使う)
```

[6] Parsingはスコープ外、[8]候補確定フェーズは3節の理由によりこのケースでは
発火しない(第2ケースで必要になる。3-4節)。

## 3. 最初に通す教材ケースの選定

### 3-1. 最初の1論点: 定額法の定義式ブロック(テーマ8-2)

`planning/parser_source_granularity_validation.md`ケース2・5、
`planning/book1_prototype_validation_results.md`ケース3で検証済みの、
**定額法の計算式が定義される1行の式ブロック(テーマ8-2)**を最初のケースとする。

選定理由(ユーザー提示の基準に沿って評価):

| 基準 | 評価 |
|---|---|
| Parserで扱いやすい | ケース2で「定義ブロック自体はStage1で決着(1行の式、単独の視覚単位)」と確認済み。トップレベルのためF3で即確定し、候補化・[8]候補確定フェーズを経由しない最短経路になる(2-4節) |
| Derived Knowledge化しやすい | `calculation_formula`のcontent構造(`rawFormula`+`structure`)が5-2節で「承認済み(最終形)」。`sourceRefs=[{role: definition}]`・`consolidation.state: single_source`という最も単純な参照パターン(6節①)に一致する |
| Exerciseへ変換しやすい | `structure.tokens`(term/operator/fraction/group/power)が既に確定済みであり、かつこの式は**分数(fraction)を含む実例**のため、5種類のトークンのうち最低2種類(term/fraction、必要なら operator)を使った並び替え問題を素直に作れる |
| 実際に学習問題として意味がある | 定額法は簿記論の基礎コースで中核的な論点であり、架空の練習用トピックではない |
| 既存の設計検証ケースとして十分理解できている | 粒度検証(ケース2・5)・データモデル検証(ケース3・4a)・Stage3の代表例(`parser_design_proposal.md`3-4節)として**複数の検証資料で繰り返し確認済み**。本コーパスで最も理解が深いケースである |
| 特殊ケースすぎない | Stage1で完結する最も単純な構造。特殊な脚注構造(固定資産買換の※1〜※5等)のような複雑さを持たない |

**唯一の非自明な点はFaithful Restoration(`fraction_split`)が必要なことだが**、
これは既知パターンとして2-2節で対応方針を示した既に検証済みの崩れであり、
未知のリスクではない。

### 3-2. 第2ケース: 定額法の複数適用(テーマ8→9、同一論点の深掘り)

新しい教材トピックを探すのではなく、**同じ定額法という論点の中で、Parser
パイプラインの残りの責務(候補提示方針・[8]候補確定フェーズ)を検証する
ケース**として、`planning/parser_source_granularity_validation.md`ケース2・
`book1_prototype_validation_results.md`ケース4aで検証済みの、**テーマ8・9の
設例内に教材明示の区切りなしで繰り返し現れる数値適用の計算行(4件以上)**を
第2ケースとする。

このケースは以下を初めて要求する。

- Stage3候補の検出(3節Stage3、パターン検出器が設例内部にネストした候補を
  検出)
- Source候補一覧レポートへの実データ登録(2-4節で「候補0件」として仮出力
  していたレポートを、実際に候補ありのケースで検証する)
- [8]候補確定フェーズ(人間レビューが「この計算行を独立参照が必要な子
  Sourceとして確定するか」を判断する、最初の実例)
- `provenance`(`relation: extracted_from_parent`)・親子`sourceFaithful`
  重複の許容(5-1節)
- Derived Knowledge側の複数Source統合(`sourceRefs`に`application`roleを
  追加、`evidence.byRole = {definition: 1, application: N}`、
  `consolidation.state: merged_confirmed`。6節②)

**推奨する進め方**: 第1ケースで作った`dk-formula-teigakuho`(仮ID)という1件の
Derived Knowledgeに対し、第2ケースでは新しいSourceを追加で紐付けるだけでよく、
Exercise・学習UI側の変更は不要と見込まれる(Derived Knowledge層より下流の
契約は変わらないため)。同じ論点を深掘りすることで、新しいトピックの調査
コストを払わずにパイプラインの残り半分(候補提示方針)を検証できる。

必要であれば、この後に**仕訳の型(`journal_pattern`)の穴埋め出題**を検証する
独立した第3ケース(例: `book1_prototype_validation_results.md`ケース2相当の
単純な仕訳型ボックス、Stage1で完結)を追加してもよいが、これはMVPの縦切りを
通す上で必須ではない(9節)。

## 4. Derived Knowledgeまでの最小実装

### 4-1. 対象knowledgeKindを1つに絞る

最初の2ケース(3節)はいずれも`knowledgeKind: "calculation_formula"`のみで
完結する。`journal_pattern`・`solution_technique`への対応は今回のMVPでは
実装しない(9節)。

### 4-2. 半自動生成 + 人間レビューという構成

CLAUDE.md原則4(推測しない)を踏まえ、Derived Knowledge候補の生成は次の
分担とする。

```
確定Source(2節で生成)
   │  半自動処理: sourceFaithfulをrawFormulaへそのままコピーし、
   │  structure.tokensを機械的に組み立てる(定額法の式は5-2節で確定済みの
   │  5種類のトークン語彙で表現できることが検証済みのため、パース自体は
   │  この1式に限れば十分単純)
   ▼
Derived Knowledge候補(contentConfidence.level は暫定的に "reconstructed"
等の低めの値にしておき、人間承認で "verified_from_source" 等へ引き上げる
運用としてもよい。5節)
   │  人間レビュー(5節)
   ▼
承認済みKnowledge(contentConfidence確定、sourceRefs確定)
```

「完全自動生成」は目指さない。トークン化ロジックがこの1式で通っても、
汎用的な式パーサーとして育てる作業は次フェーズ以降の課題とする。

### 4-3. 最小限守るべき制約

- `sourceRefs`は必ず2節で生成した確定Sourceの`sourceBlockId`を参照する
  (架空の参照を作らない、CLAUDE.md原則3)。
- `rawFormula`は`sourceFaithful`と一致させる(要約・言い換え禁止、原則2)。
- 判断に迷うフィールド(`contentConfidence.level`の具体的語彙等、
  `source_derived_knowledge_design_proposal.md`12節で「まだ判断されていない
  事項」とされているもの)は、無理に確定値を選ばず、暫定値であることが
  分かる形で保持する(原則4)。

## 5. 人間レビュー画面の最小要件(開発用確認UIから段階的に育てる)

**(今回の修正)** ユーザーから、M1〜M2の途中または直後に、実データをブラウザ上で
確認できる最低限の画面を先に置きたいという要望を受けた。これに応じ、
「レビュー画面」を最初から1つの完成形として作るのではなく、**5-1(閲覧のみ)
→5-2(操作を追加)という2段階**で育てる構成に変更する。5-1が8節・10節での
「最初にブラウザ上で確認できる地点」、5-2が「最初に何らかの操作ができる地点」
に対応する。

### 5-1. 開発用確認UI(閲覧のみ、最初に作るもの)

**目的は「Parserが何を読み取り、最終的に何が問題生成の材料になっているかを
ユーザー自身が確認できること」のみ。** デザイン・汎用性・複数件の一覧管理は
求めない(1ケース分を1画面で縦に並べて表示できれば十分)。

表示すべきデータの流れ(ユーザー指定どおり):

```
PDF上の元データ(location: ページ番号等の参照)
   ↓
抽出結果(extractionRaw。sourceFaithfulと一致し省略されている場合はその旨を表示)
   ↓
sourceFaithful(Faithful Restorationでの補正内容が分かるよう、extractionRawとの
   差分・diag.faithfulReconstructionの情報も併記できると尚よい)
   ↓
確定Source / Source候補(このケースは確定Sourceのみ。3-1節)
   ↓
Derived Knowledge候補(content.rawFormula・structure・sourceRefs・
   contentConfidence・evidence)
```

**着手タイミング**: [a](Parser最小プロトタイプ)の完了直後に、まず
「PDF上の元データ→抽出結果→sourceFaithful→確定Source」までを表示できる形で
着手してよい。[c](Knowledge候補生成)の完了を待たずに着手でき、[c]完了後に
「Derived Knowledge候補」の表示を追記すればチェーン全体が完成する
(1-1節参照)。この段階では**操作(承認/修正/除外)は実装しない**。

### 5-2. 承認 / 修正 / 除外操作の追加(5-1の画面を発展させる)

5-1の画面に、次の3操作を追加する形で発展させる(新しい画面を別途新設しない)。

| 操作 | 内容 |
|---|---|
| 承認 | `contentConfidence.level`を確定値へ更新し、公式Knowledgeとして確定する |
| 修正 | `content`または`sourceRefs`を人間が書き換える(誤ったトークン化の訂正等) |
| 除外 | 「Derived Knowledgeとして採用しない」という判断を明示的に記録し、無かったことにせず理由付きで保持する(原則4) |

**最初の実装では、複数候補の一覧管理・検索・フィルタ等は不要。** 対象が1件
(第2ケース実施後でも数件)であるため、1件ずつ表示して操作できれば十分。
第2ケース(3-2節)で[8]候補確定フェーズが必要になった際は、Source候補一覧
レポートの1エントリ(独立参照が必要かどうかの判断)についても、同じ画面の
延長で「この計算行を独立Sourceとして確定するか」を承認/却下する操作を
追加する形で対応できる見込みである(独立した別画面を新設する必要はない)。

## 6. Exercise生成の最小スコープ

### 6-1. 既存資産の再利用可能性の評価

`planning/boki-app-integration-proposal.md`4節の評価を踏まえると、Zaihyo
Parser(html-v2)の資産のうち、**データ構造に依存しない部分**(ExerciseView
のレジストリパターン、`progressStore.js`・`themeStore.js`・`dragReorder.js`)
は流用候補になる。一方、**出題形式のデータモデル自体**(`ordering`の
`assembledFromSource`前提)は、SPEC.md5節・CLAUDE.mdの既存判断どおり流用
しない(公式の並び替えは「言語表現/文字式のペア」という新モデルが必要)。

**MVPで現実的に再利用できるのは「レジストリパターン」と「drag&dropの
UI部品」の2つ**であり、出題データのスキーマ自体は3節のケースに合わせて
新規に最小設計する。

### 6-2. 最小スコープ

- 出題形式は**並び替え1種類のみ**(`structure.tokens`をシャッフルして提示し、
  正しい順序に並べ替えさせる)。穴埋め形式は実装しない(`journal_pattern`
  対応は9節で後回し)。
- 出題データは**承認済みKnowledge 1件から生成する1問のみ**。ランダム出題・
  複数問のプールは不要。
- 採点ロジックは「トークン列が`structure.tokens`の正解順序と一致するか」の
  単純な文字列/配列比較でよい。

### 6-3. レジストリ設計の先取りについて

SPEC.md5節(出題形式を固定しない)を踏まえ、Exercise生成そのものは
レジストリパターンを踏襲した設計にしておくことを推奨する(ハンドラが
1つしかなくても、2つ目を追加する際にコア部分を書き換えずに済むため)。
ただし**これは最小限の型の話であり、正式なレジストリ機構の作り込みは
不要**(2つ目のハンドラが実際に必要になってから拡張すればよい)。

## 7. 最小学習UI

ユーザーが実際に「問題を解く」体験をする最初の画面(Point 3)。

- **問題を見る**: `structure.tokens`をシャッフルした状態で表示する(6-2節)。
- **回答する**: drag&drop(または単純なクリック選択+並べ替え)でトークンを
  並べ替える。
- **正誤を見る**: 6-2節の単純比較で正誤判定し、結果を表示する。
- **正解・解説を見る**: 正しい順序(`structure.tokens`の正解形)と、
  `rawFormula`(教材上の忠実な表現。正本)を並べて表示する。加えて、
  `sourceRefs`経由でどのSource(教材のどの箇所)に基づく問題かを表示できると、
  原則3(出典追跡)が学習UI側でも一貫する。

**進捗保存・学習履歴・未修得管理は含めない**(9節)。1問を解いて結果が
見えれば、この段階のゴールは達成される。

   ▼

   │

   [8]候補確定フェーズ・Derived Knowledgeの複数Source統合を検証

### 10-2. 3地点の明示(今回の修正で更新)

- **Point 1. 最短でブラウザ上で確認できる地点**: **M3(開発用確認UI)**。
  M1完了直後から着手でき、PDF元データ→抽出結果→sourceFaithful→確定Source
  までは表示できる(Knowledge候補の表示はM2完了後に追加)。デザイン・操作は

  除外操作を追加し、承認操作を実行してM2の候補が公式Knowledgeとして確定した
  時点。
- **Point 3. 最短で実際の問題を1問解ける地点**: **M6**。最小学習UIで並び替え
  問題1問を実際に解き、正誤・解説まで確認できた時点。これが縦切りMVPの最終
  ゴールである。
