# 簿記論アプリ 設計メモ(進行中)

このファイルは、財表パーサーの派生として「簿記論アプリ」を作る計画についての
これまでの相談内容をまとめたものである。

新しいセッション(特にローカルのClaude Code / Cowork)でこの作業を再開する場合は、
まずこのファイルを読むこと。

---

## 1. 目的

問題集をそのまま構造化データへ変換するのではなく、
「最も効果的な簿記論の問題集」を作ることが目的である。

簿記論を解くための本質は次の2つである。

- 仕訳の型を覚えていること(穴埋め形式)
- 数値を求めるための公式を覚えていること
  (言語による公式と、文字式による計算式の両方) (並び替え形式)

この2つを高速で回転させることで、
どんな出題形式にも耐えうる本質的な簿記力が養われる、という仮説にもとづく。

問題生成AIを作ることが目的ではない。
Knowledge Baseを作ることも今回はスコープ外(財表パーサーのFirst Taskと同じ考え方)。

---

## 2. 財表アプリとの違い(重要)

財表パーサーの原則5(原文を失わない。AIによる要約・言い換えは禁止)は、
簿記論では単純には適用できない。

理由:

- 仕訳の型は教材に明示されていることが多い
- しかし、算定方法の公式・一般式・文字式は、
  教材に必ずしもそのままの形で書かれているとは限らない
- 目的は「重複する内容を1つの式・考え方に統合し、
  汎用的・網羅的な知識としてコンパクトに整理すること」であり、
  これは個々の問題の原文をそのまま保存するだけでは達成できない

### 採用する設計方針

データを2つのレイヤーに分離する。

1. **原文保持レイヤー**
   個々の例題・仕訳・解説など、教材原文そのまま(財表パーサーと同じ原則)。

2. **知識統合レイヤー(派生データ)**
   型・公式など、複数箇所から統合・一般化した知識。
   ただし必ず「どの原文箇所(原文保持レイヤーのどの項目)から抽出したか」という
   出典参照を持たせる。根拠のない創作(推測)はしない。
   原則6(推測しない/unknownとして保存する)は、この派生データにもそのまま適用する。
   出典を辿れない・確信が持てないものはunknownとして保存し、無理に統合しない。

## 3. 教材について

### 教材の種類

問題集ではなく**教科書**を使う。

理由:
- 教科書はすでに公式・型を一般化された形で明示していることが多く、
  「書かれているものを構造化する」作業に近い(原則6を守りやすい)
- 問題集から複数例題を横断して一般式を合成するのは、
  実質的に「書かれていないものを合成する」作業になりやすく、リスクが高い

問題集は、型・公式の妥当性検証や、ドリル用の具体例(数値バリエーション)を
増やす目的で、後の段階で活用する。

### 教材のボリューム

- 基礎コース: 4冊
- 上級コース: 4冊
- 合計8冊。内容の重複・新規部分が多く混在する。

複数の教科書(特に基礎〜上級)に共通して出てくる型・公式は、
「本質的なパターンである」ことの裏付けとして扱ってよい。
逆に上級だけに出てくるものは応用パターンとして区別する。

## 4. 実装方針

既存の財表パーサーのパイプライン
(PDF → Parser → BookStructureMaster(BSM) → ExerciseView → html-v2)
を再利用・拡張する形で進める(ゼロからの新規プロジェクトにはしない、ユーザー承認済み)。

参考: 既存の出題形式(html-v2/js/registry.js)
- `single_blank` / `multi_blank`: 穴埋め → 仕訳の型ドリルに転用できそう
- `ordering`: 並び替え → 公式ドリルに転用できそうだが要注意

### 要注意点: `ordering`の現状実装

現状の`ordering`ハンドラは「元の一文の文節を並べ替えて復元する」設計
(`assembledFromSource`)になっている。

しかし公式ドリルでは「同じ公式」に対して
**言語表現**と**文字式**という2つの異なる表現をセットで出題したい。
これは単一原文の文節並べ替えとは構造が異なるため、
そのまま流用せず、新しい出題形式(またはorderingの拡張)として
設計し直す必要がある。

## 5. 進め方(フェーズ)

CLAUDE.mdの開発方針(設計を優先する、巨大なスクリプトを作らない、
途中成果物を残しながら進める)に従い、8冊を一度に処理しない。

1. 基礎コース1冊目のみを対象に、PDF調査 → 型・公式抽出パイプラインの
   中間データ設計案を作る
2. 設計案をユーザーに提示し、承認を得る
3. 承認後、1冊目で実際にパイプラインを動かし、結果を確認する
4. 問題なければ、同じパイプラインを残り7冊に適用してスケールする

途中で設計ミスが見つかった場合の手戻りを最小化するため、
最初から全8冊に着手しない。

---

## 6. 教材データの取り扱いについて

教材PDFは有償ライセンス教材であり、財表パーサーの`.gitignore`と同じ考え方で、
**リポジトリには一切コミットしない**。

- 原本PDFは `/input/` に置く(既に`.gitignore`で除外設定済み)
- 抽出後の中間データ・派生データも、教材原文を含む限りコミット対象外とする
  (財表パーサーの`/output/`と同じ扱いを踏襲する想定。正式なディレクトリ名は
  実装時に改めて決める)

このメモ自体は教材原文を含まないため、通常どおりコミットしてよい。
