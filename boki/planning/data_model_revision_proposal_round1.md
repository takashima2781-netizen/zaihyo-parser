# データモデル改訂案(第1弾)

`planning/book1_prototype_validation_results.md`で見つかった4つの弱点に
対する改訂案。サンプルは架空データ(実在しない勘定科目・数値)を用いる。

**確定について**: 本提案は`planning/data_model_revision_round1_recheck.md`
での再検証(ケース2・3・4a・5・8を実データで埋め直す確認)を経て、
`group`・`power`トークン種別の追加を含めて内容が確定した。確定した
内容は`planning/source_derived_knowledge_design_proposal.md`(正式設計)
へ反映済み。本ファイルは「なぜこの構造に至ったか」という検証記録として
残す。

## 1. calculation_formula / solution_technique のcontent構造

### 1-1. 実データで何が問題だったか

- ケース3(定額法)で、`termsRaw`のようなフラットな用語配列では、
  「1年」と「耐用年数」が**分数(除算)の関係にある**ことを表現できず、
  `(A－B)×(C／D)＝E`と`(A－B)×C×D＝E`が区別できなくなっていた。
- ケース5(方程式)で、`rawExample`という単一文字列に式変形の全過程
  (`Ｘ－0.24Ｘ＝91,200` → `0.76Ｘ＝91,200` → `Ｘ＝120,000`)を詰め込む
  しかなく、ステップ数・各ステップの内容を後から機械的に扱えなかった。

### 1-2. 最小限の変更提案

**3つの異なる概念を明確に分離する**(今回の指摘を踏まえ、混同しない):

1. **教材上の忠実な式表現**: `rawFormula`/`rawExample`。常に必須。
   これが唯一の正本(SSOT)であり、以下の`structure`・`steps`は
   あくまでこれを補助する**任意の**構造化情報にとどめる。
2. **構造化された式**: 新設する`structure`(任意)。**汎用的な数式ASTは
   作らない。** 再検証の結果、本冊(No.1巻)の実データを欠落なく表現する
   ために最低限必要と確認できたのは「項(term)」「演算子(operator)」
   「分数(fraction、分子/分母を持つ)」「括弧グループ(group、丸括弧に
   よる明示的なグルーピング)」「べき乗(power、base/exponentを持つ)」
   の**5種類**。`group`は、原文の丸括弧が「演算子の優先順位どおりに
   読むと原文と異なる結果になる箇所」を明示するために必要と判明した
   (例:「（取得原価－残存価額）×分数」を`group`なしで表現すると、
   優先順位どおりに読んだ場合と区別がつかなくなる)。**`group`で
   明示的に囲まれていないトークン列は、通常の数式と同じ演算子優先順位
   (×・÷は－・＋より先に結合する)で読む、という解釈規約を前提とする。**
   `power`は、指数を含む式(例: 定率法を複数年分まとめて計算する式)を
   表現するために必要と判明した。トークン種別自体は引き続きopen
   vocabularyであり、この5種類を将来にわたる固定enumとはしない。
   No.2巻以降で新しい崩れ方が見つかれば、同じ仕組みでトークン種別を
   追加する。
3. **学習用に利用する表現**: 今回は設計しない。Exercise層の責務であり
   (設計案6節のとおり詳細設計はまだ行わない)、`structure`があれば
   将来設計しやすくなる、という位置づけに留める。

**方程式・複数ステップ**については、`structure`とは別に、
`solution_technique`の`content`へ`steps`(任意の配列)を追加する。各
ステップは「その時点での式の忠実な表現」を保持するだけの最小構成とし、
ステップ単位の`structure`は今回は設けない(必要になれば後で追加できる)。

### 1-3. 変更後の抽象データ例(架空)

```jsonc
// calculation_formula(架空: 「対象額－既計上額」型の式)
{
  "knowledgeKind": "calculation_formula",
  "content": {
    "rawFormula": "（対象額－既計上額）×（１期間／全期間）＝当期計上額",  // 正本。常に必須
    "structure": {                      // 任意。分数を含む場合のみ意味を持つ
      "kind": "sequence",               // open vocabulary
      "tokens": [
        { "kind": "term", "value": "対象額" },
        { "kind": "operator", "value": "－" },
        { "kind": "term", "value": "既計上額" },
        { "kind": "operator", "value": "×" },
        { "kind": "fraction",
          "numerator":   [{ "kind": "term", "value": "１期間" }],
          "denominator": [{ "kind": "term", "value": "全期間" }] },
        { "kind": "operator", "value": "＝" },
        { "kind": "term", "value": "当期計上額" }
      ]
    }
  }
}

// solution_technique(架空: 未知額Ｙを方程式で逆算する例)
{
  "knowledgeKind": "solution_technique",
  "content": {
    "rawExample": "Ｙ－0.3Ｙ＝70,000 → 0.7Ｙ＝70,000 → Ｙ＝100,000",  // 正本
    "steps": [                          // 任意。複数ステップがある場合のみ
      { "rawStep": "Ｙ－0.3Ｙ＝70,000" },
      { "rawStep": "0.7Ｙ＝70,000" },
      { "rawStep": "Ｙ＝100,000" }
    ],
    "technique": "linear_equation_backsolve"
  }
}
```

### 1-4. 既存モデルへの影響範囲

Source層(ContentBlock)には影響しない(`sourceFaithful`はそのまま)。
Derived Knowledgeの`content`のみへの追加であり、既存フィールド
(`rawFormula`/`rawExample`)は削除・変更しない。`structure`・`steps`は
いずれも**任意**のため、既存の(structureを持たない)想定データとの
後方互換性は保たれる。

### 1-5. 過剰設計になるリスク

`structure`のトークン種別を最初から多く用意しすぎると、結局「汎用的な
数式AST」に近づいてしまう。今回は`term`/`operator`/`fraction`の3種類
だけに絞ることで、このリスクを避ける。`steps`も、ステップごとの
構造化(structure)までは今回踏み込まない。

### 1-6. 今決めるべき部分(再検証により確定)

- `structure`を「任意」とし、無い場合は`rawFormula`/`rawExample`のみで
  正当なデータとみなす、という原則。
- トークン種別を`term`/`operator`/`fraction`/`group`/`power`の5つとする
  こと(実データによる必要性確認済み。固定enumにはしない)。
- `group`で明示的に囲まれていない箇所は演算子優先順位で読む、という
  解釈規約。

### 1-7. No.2以降まで保留できる部分

- `term`/`operator`/`fraction`/`group`/`power`以外の新しいトークン
  種別が必要になるかどうかの判断。
- ステップ単位の`structure`が必要かどうか。
- `structure`を自動生成するのか、人手で作るのかというParser実装上の判断。

## 2. sourceRefsとevidence

### 2-1. 実データで何が問題だったか

ケース4aで、定額法の公式が「テーマ8-2で1回定義され、その後は定義を
再掲せず複数箇所で数値適用されるだけ」という構造になっていることが
判明し、`sourceRefs`が「定義」と「適用」を区別できず、
`evidence.occurrenceCount`が両者を合算すべきか別々に数えるべきか
不明だった。

### 2-2. 最小限の変更提案

`sourceRefs`の各要素へ`role`を追加する(open vocabulary。ユーザー提示の
4語を初期候補とするが、`application`と`example`が実際に区別できる
概念か、今後のデータで判断する):

- `definition`: この知識が一般的な形で定義されている箇所
- `restatement`: 定義がほぼそのまま再掲されている箇所
- `application`: 定義を再掲せず、数値等を当てはめて適用している箇所
- `example`: 設例全体としてこの知識を用いている箇所(`application`との
  違いが実データで確認できなければ、将来どちらかへ統合してもよい)

`evidence.occurrenceCount`という単一の数値は廃止し、
**`role`ごとの内訳を持つ**構造に変更する。単一値への集約を強制しない。

### 2-3. 変更後の抽象データ例(架空)

```jsonc
{
  "knowledgeKind": "calculation_formula",
  "sourceRefs": [
    { "sourceBlockId": "block-X1", "role": "definition" },
    { "sourceBlockId": "block-X2", "role": "application" },
    { "sourceBlockId": "block-X3", "role": "application" },
    { "sourceBlockId": "block-X4", "role": "application" }
  ],
  "evidence": {
    "byRole": {
      "definition": 1,
      "application": 3
    },
    "distinctThemes": ["theme-A", "theme-B"],
    "distinctBooks": ["book-1"],
    "crossesBaseAdvanced": false
  }
}
```

### 2-4. 既存モデルへの影響範囲

`sourceRefs`要素への`role`追加、`evidence.occurrenceCount`から
`evidence.byRole`への変更。第2版で設計した3軸モデル
(contentConfidence/evidence/consolidation)の骨格自体は変更しない。
`evidence`は3軸のうちの1軸(B軸)の内部構造の見直しに限定される。

### 2-5. 過剰設計になるリスク

roleの語彙を最初から細かく分けすぎると、実際の分類作業(このSourceは
definitionかapplicationか)に迷いが生じ、かえって手間が増える。4つの
候補のうち、実際に使い分けが機能するかは実データで検証しながら
語彙を整理していく前提とする。

### 2-6. 今決めるべき部分

- `sourceRefs`に`role`を持たせること、`evidence`を単一countから
  role別内訳へ変更すること、という構造の方向性。

### 2-7. No.2以降まで保留できる部分

- `role`語彙の最終確定(`application`と`example`を統合するかどうか等)。
- `evidence.byRole`をもとに`consolidation.state`をどう判断するか
  (これは今回も「機械的な閾値にしない」という既存方針を維持し、
  引き続き人間判断の材料とする)。

### 2-8. 再検証で判明した重要な前提条件(Parser設計への申し送り)

再検証(`planning/data_model_revision_round1_recheck.md`)で、
`sourceRefs`の1要素が1つの`role`だけで自然に分類できたのは、**Source
ブロックの粒度を脚注(`※1`・`※2`等)のような意味単位まで細かく分割して
いたことが前提**だと判明した。粒度が粗く「設例全体」を1つのSourceブロック
として扱った場合は、同じブロックが「知識の具体例(example)」と「数値を
当てはめた適用(application)」の両方に見える可能性が高い。**この前提
条件は、Derived Knowledgeモデル自体を変更する理由にはしないが、次の
Parser設計(Source粒度の設計)で必ず考慮すべき制約として申し送る**
(正式な申し送り先は`source_derived_knowledge_design_proposal.md`の
該当節を参照)。

## 3. journal_patternのplaceholder

### 3-1. 実データで何が問題だったか

ケース2で、`○○○`(勘定科目未定のプレースホルダ)を`creditAccounts`
配列へそのまま文字列として入れると、実在する科目名(例:「繰入費用」)と
「科目が未定であることを示す記号」が型として区別できなかった。また、
科目のプレースホルダ情報と、既存の`placeholders`配列(元は金額
プレースホルダ`×××`のみを想定)が二重管理になり、どちらが正か
未定義だった。

### 3-2. 最小限の変更提案

`debitAccounts`/`creditAccounts`の配列要素を、単純な文字列から
**「確定値か、プレースホルダか」を区別する最小限の型**へ変更する。
巨大なplaceholder専用の型は作らず、次の2パターンのみを区別する。

- `{ kind: "fixed", value: "<科目名>" }`: 教材に具体的な科目名が
  明記されている。
- `{ kind: "placeholder", token: "<教材上の記号>", undetermined:
  "account_name" }`: 科目自体が教材上不定(`○○○`等)。

金額側のプレースホルダ(`×××`)は、勘定科目の確定/未定とは別の関心事
(勘定科目は確定していても金額は常に未定、というのが通常のパターン)
であるため、既存の`placeholders`配列は**金額スロットに限定**し、
`amountSlots`へ改称する。これにより、科目の確定/未定は
`debitAccounts`/`creditAccounts`側の`kind`で、金額のプレースホルダは
`amountSlots`側で、それぞれ単一の場所にのみ記録される(二重管理を解消)。

### 3-3. 変更後の抽象データ例(架空)

```jsonc
{
  "knowledgeKind": "journal_pattern",
  "content": {
    "rawTemplate": "(借) 繰入費用 ××× (貸) ○○○ ×××",  // 架空例
    "debitAccounts": [
      { "kind": "fixed", "value": "繰入費用" }
    ],
    "creditAccounts": [
      { "kind": "placeholder", "token": "○○○", "undetermined": "account_name" }
    ],
    "amountSlots": [
      { "token": "×××", "role": "amount" }
    ]
  }
}
```

### 3-4. 既存モデルへの影響範囲

`journal_pattern`の`content`内部のみの変更。旧`placeholders`配列は
`amountSlots`へ改称・スコープ限定(実質的にはrole:"account"だった
要素が無くなり、role:"amount"のみになるため、`role`フィールド自体は
将来単純化できる可能性があるが、今回は互換のため残す)。

### 3-5. 過剰設計になるリスク

`undetermined`の値を細かく分類しすぎない(今回確認できたのは
`account_name`が不定になるケースのみ)。将来「借方・貸方どちらに
なるか自体が不定」のようなケースが出てきたら、その時点で語彙を
追加する。

### 3-6. 今決めるべき部分

- `debitAccounts`/`creditAccounts`の要素を`{kind, value|token}`型に
  すること。
- 金額プレースホルダを`amountSlots`として科目のプレースホルダと
  分離すること。

### 3-7. No.2以降まで保留できる部分

- `undetermined`の語彙の拡張(他の「何が不定か」のパターンが今後の
  教材で見つかるか)。

## 4. ケース8: 表構造とスパン単位の注釈(2問題に分離)

### 4-A. 表そのものの構造をSourceとしてどう保持するか

#### 実データで何が問題だったか

`blockKind: "table"`という種別は候補に挙げていたが、`content`の具体的な
構造を一度も設計しておらず、4方式×複数行の比較表を前にして、
単純な文字列保持以上にどう構造化すべきか判断できなかった。

#### 最小限の変更提案

行・列・セルの**単純な2次元グリッド**として保持する。セルの結合・
入れ子・セル内部のさらなる構造化は行わない(セルの中身は忠実な文字列
のまま保持し、必要ならそのセル自体を将来別のContentBlockとして
参照させることもできるが、今回はそこまで踏み込まない)。

#### 変更後の抽象データ例(架空: 4方式の比較表)

```jsonc
{
  "blockKind": "table",
  "sourceFaithful": "...(表全体の忠実なテキスト。正本)",
  "content": {
    "columnHeaders": ["方式A", "方式B", "方式C", "方式D"],  // 架空
    "rowHeaders": ["期首", "仕入時", "決算整理前", "決算整理後"],  // 架空
    "cells": [
      ["...", "...", "...", "..."],
      ["科目Ｘ／科目Ｙ", "科目Ｘ／科目Ｚ", "...", "..."],
      ["...", "...", "...", "..."],
      ["...", "...", "...", "..."]
    ]
  },
  "diag": {
    "note": "セル内の／は本表の文脈では簡略仕訳表記(借方／貸方)として使われている"
  }
}
```

`diag`に「この表全体で／をどう解釈すべきか」という**表単位の注記を
1つだけ**持たせれば十分であり(4-B節参照)、セルごとに個別の解釈情報を
持たせる必要はなかった。

#### 既存モデルへの影響範囲

`table`という新しいblockKindの`content`構造を初めて具体化するのみ。
他のblockKindには影響しない。

#### 過剰設計になるリスク

セルの結合・多階層見出し等、複雑な表組みへの対応を今回作り込まない。
本冊で確認した表はいずれも単純な行×列のグリッドで表現できており、
それ以上の複雑さへの対応が必要になった時点で拡張する。

#### 今決めるべき部分

- `table`のcontentを行見出し・列見出し・セルの2次元配列という最小限の
  グリッドで表現すること。

#### No.2以降まで保留できる部分

- セル結合・多階層見出しなど、より複雑な表への対応。
- セル単位でContentBlockとして独立させる必要があるかどうか。

### 4-B. ブロック内部の「／」等、文脈依存の意味をどう保持するか

#### 実データで何が問題だったか

為替レート表記(「118円／ドル」)が、独立したブロックではなく
`worked_example`の問題文プロパー文の一部として出現し、ブロック単位の
`parsed`では特定の記号だけを狙って注釈できなかった。

#### 検討結果: 新しい概念は提案しない

指示のとおり、まず既存構造で対応できないかを検討した。結論として、
**新しいスパン注釈の仕組みは不要**と判断する。理由は次のとおり。

- 為替レートの「／」は、そもそも**構造化して解釈する必要がない**。
  仕訳の借方/貸方を機械的に読み取るために「／」の意味を判定する必要が
  あるのは、**仕訳表記が期待される文脈(journal_templateブロックや、
  4-Aのようなtableのセル)に限られる**。それ以外の場所(通常の
  `worked_example`の問題文プロパー等)に出てくる「／」は、単に
  `sourceFaithful`の地の文の一部として保持すればよく、意味の解釈自体を
  試みる必要がない。
- したがって、「／」の意味判定は**ブロック単位の`parsed`の役割を
  拡張する話ではなく、そもそもどのblockKind/contextで意味判定を試みる
  べきかという運用方針の話**である。この方針(仕訳表記が期待される
  文脈でのみ判定を試みる)を`diag`または実装ガイドラインとして明記
  すれば足り、スキーマへ新しいフィールドを追加する必要はない。

#### 既存モデルへの影響範囲

なし(スキーマ変更なし)。運用方針としての注記のみ。

#### 過剰設計になるリスク

**この項目自体が「過剰設計を避けた」結論**である。1ケースのためだけに
汎用スパン注釈の仕組みを導入しなかった。

#### 今決めるべき部分

- 「記号の意味解釈は、仕訳表記が期待される文脈(journal_template・table
  のセル等)に限定して試み、それ以外の地の文では試みない」という
  運用方針を明記すること。

#### No.2以降まで保留できる部分

- 「仕訳表記が期待される文脈」以外でも記号の意味解釈が必要になる具体的な
  実例が今後見つかった場合、その時点で改めてスパン注釈の要否を検討する。

## 全体の見解(再検証を経た最終結論)

`planning/data_model_revision_round1_recheck.md`で、ケース2・3・4a・5・8
を改訂後の構造で実際に埋め直して確認した。結果は次のとおり。

- ケース2(プレースホルダ) → **解消した**。
- ケース3(分数の構造) → 当初のterm/operator/fractionの3種のみでは
  **一意に読めないことが判明**(丸括弧のグルーピング情報が失われる)。
  `group`トークン種別の追加により**解消**。
- ケース4a(定義/適用・evidence) → **解消した**(ただし脚注単位の細かい
  Source粒度が前提、という条件付き。2-8節参照)。
- ケース5(複数ステップ・分数/指数) → `steps`は解消。指数は`power`

### 追加の再検証は必要か

**不要と判断する。** 1回目(4項目の構造変更)、2回目(トークン種別2つの
追加)と、検証を重ねるごとに必要な変更が小さくなっており、これ以上
同規模の検証を重ねても得られる情報は逓減すると考えられる。

### Parser設計へ進んでよいか

**進んでよいと考える。** 今回の変更はいずれもSource/Derived Knowledgeの
大枠(StructureNode/ContentBlock、4概念、3軸状態モデル、open vocabulary)
を変更するものではなく、`content`・`sourceRefs`・`evidence`という詳細
レベルの拡張に留まる。ただし、2-8節の「Source粒度の前提条件」は、
Parser設計(Source粒度をどこまで細かく分割するかの設計)の初期段階で
必ず考慮する必要がある。
