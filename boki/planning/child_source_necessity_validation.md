# 子Source化候補の必要性判定基準 小規模実データ検証

`planning/parser_design_proposal.md`3-5節・9節で保留されていた「Stage2/3で検出
された候補を実際に子Source化する必要があるかどうかの判断基準」について、既存の
検証記録(`planning/parser_source_granularity_validation.md`)と今回の
`planning/pattern_detection_survey.md`から選んだ実データケースを用いて検証した
結果である。

**本ファイルは検証結果の報告のみである。** Stage3判定基準の正式確定・Parser本体
実装・正式スキーマのコード化・gateChecks本実装・Derived Knowledge生成には一切
進んでいない。`parser_design_proposal.md`自体もまだ書き換えていない。
`pattern_detection_survey.md`で見つかった既存資料との4件の食い違いも、今回は
修正していない(ユーザー指示どおり、この検証終了後に別途判断する)。

---

## 1. 検証目的

`pattern_detection_survey.md`の結果、次の3つが別問題であることが明確になった。

1. pattern detectorが候補を検出したこと
2. その候補が教材上の意味的に完結した単位であること
3. その候補を親Sourceとは別のSourceとして独立参照する必要があること

今回は「何を検出するか」ではなく、**検出された候補をどの条件なら独立した子Source
として切り出す必要があるのか**を、実データの比較から検証する。Stage3「パターン
検出によるネスト単位の子Source化」について、

- 子Source化が必要なケース
- 子Source化しない方が自然なケース
- どちらとも判断できずレビューが必要なケース

を実データから比較し、必要性判定基準の**候補**を具体化する。最終ルールとしては
固定しない。

---

## 2. 前提

- 1(検出)を満たしただけで2(意味的完結性)・3(独立参照必要性)を満たすとは扱わない。
  この3つを本検証全体を通じて区別する。
- 反復回数・テーマ横断性は**観察事実・判断材料**として記録するが、直接の決定条件
  にはしない(「複数回出現したから子Source化する」「1回しか出ないから子Source化
  しない」という判定は採用しない)。
- 「計算式だから子Source」「仕訳だから子Source」「パターン検出されたから子Source」
  のような、blockKind・出現回数だけによる単純ルールは avoid する。今回知りたいのは
  種類ではなく「独立Sourceとして切る必要性」を決める条件である。
- `sourceRefs.role`の割り当て・Derived Knowledgeとの同一性判定は、既存設計
  (`parser_design_proposal.md`4-2節)どおりParserの責務外として扱い、本検証でも
  行わない。

## 4. 判定軸

以下は「採用するルール」ではなく、実データに当てて有効性を評価する候補軸である。

1. **意味的完結性**: その部分だけを`sourceFaithful`として読んでも意味が成立するか
2. **独立参照必要性**: Derived Knowledge等から、その部分だけを一意に参照する必要が
   ありそうか(role割り当て・Knowledge同一性判定そのものは行わない)
3. **親から切り離した場合の文脈損失**: 子だけでは意味が不足したり、表・設例・解説
   全体との関係が壊れないか
4. **教材上の境界**: `※1`等の明示的境界があるか(ないことだけを理由に子Source化
   不可とはしない)
5. **検出・復元の安定性**: 分数・指数・縦積み`○○○`等について、Faithful
   Restoration後に安定した単位として切り出せるか
6. **親子重複の許容可能性**: 子Source化すると親`sourceFaithful`との重複が発生する
   場合、既存方針(重複許容+`diag.provenance`+`relation`別gateChecks)で扱える範囲か

## 5. ケース別結果

### A1. 定額法の設例内計算式適用 → **A(子Source化が必要)**

テーマ8-2で用語ベースの抽象式が1回定義され、後続の複数設例(テーマ8・9)の解説内で、
抽象式を再掲せず数値を当てはめた計算行(例: `80,000×１年／8年＝10,000`)が繰り返し
現れる(`pattern_detection_survey.md`4-2節で16ページに分布することを確認済み)。

| 軸 | 評価 |
|---|---|
| 1. 意味的完結性 | **低い**。計算行単体(`80,000×１年／8年＝10,000`)は、取得原価が何の資産かという前提情報が親(設例)の文脈にしかなく、単独では意味が完結しない |
| 2. 独立参照必要性 | **高い**。設例全体を参照対象にすると、「この設例という事例(example)」と「定額法公式の適用(application)」が同じ`sourceBlockId`を指すことになり区別できなくなる |
| 3. 文脈損失 | 高い(子だけでは何の計算か分からない) |
| 4. 教材境界 | なし。教材は計算行を`※1`等の記号で明示的に区切っていない |
| 5. 検出安定性 | 中程度。単一行に収まる適用例(157・158ページ等)は安定しているが、二重分数を伴う月割計算(171〜174ページ)では抽出が不安定になる場合がある(C3で詳述) |
| 6. 重複許容可能性 | 子(計算行)の文字列が親(設例全文)に部分文字列として含まれる。`relation: extracted_from_parent`+包含チェックで対応可能な範囲(既存方針でカバー済み) |

**注目点**: 軸1(意味的完結性)は低いにもかかわらず、軸2(独立参照必要性)が高いために
「必要」と判定される。**軸1が低いことは、子Source化を妨げない。**

### A2. 固定資産買換 ※1〜※5 → **A(子Source化が必要)**

借方・貸方が複数行にわたり、`※1`〜`※5`という教材明示の記号で複数の脚注付き補足式
が1つの仕訳ボックスにぶら下がる、より複雑な型。

| 軸 | 評価 |
|---|---|
| 1. 意味的完結性 | **高い**。各脚注はそれ自体で独立した算定内容として意味が完結する |
| 2. 独立参照必要性 | 高い。各脚注が独立した`calculation_formula`または`note`候補として参照できる |
| 3. 文脈損失 | 低い。脚注は教材上もともとボックス本体とは別の場所に記載されており、親への依存が最小 |
| 4. 教材境界 | **高い**。`※1`〜`※5`という記号が教材自身に明示されている |
| 5. 検出安定性 | 高い。`※N`という記号自体は機械的検出が容易(既存検証で確認済み) |
| 6. 重複許容可能性 | 重複なし(脚注記号と脚注本体はそもそも教材上別の場所)。`relation: footnote_of_parent`+参照存在チェックで対応可能 |

**注目点**: A1と同じ「A(必要)」判定だが、A1は軸1が低く軸2が高いために必要と
判定されたのに対し、A2は軸1〜4がすべて揃って必要性を裏付けている。**同じ
「必要」判定でも、到達する軸の組み合わせは異なる。**

### B1. 方程式の複数ステップ → **B(子Source化しない)**

`Ｘ－0.24Ｘ＝91,200`→`0.76Ｘ＝91,200`→`Ｘ＝120,000`のような複数ステップの式変形
(186ページ)。1つの`solution_technique`の`parsed.steps`で保持する方が自然だった
ケース。

| 軸 | 評価 |
|---|---|
| 1. 意味的完結性 | **低い**。各ステップは前のステップからの導出であり、単体では意味が完結しない(ステップ2はステップ1に依存) |
| 2. 独立参照必要性 | **低い**。ステップ単体を独立参照する実用的理由がない |
| 3. 文脈損失 | 高い。分割すると導出の連続性(依存関係)を失う |
| 4. 教材境界 | なし |
| 5. 検出安定性 | 該当薄い(分割しないため) |
| 6. 重複許容可能性 | 該当なし |

**注目点**: A1と同じく軸1は低いが、A1と違って**軸2も低い**ため「不要」と判定
される。A1とB1を対比すると、**軸1(意味的完結性)単独では判定を説明できず、軸2
(独立参照必要性)が実質的な分岐点になっている**ことが分かる。

### B2. 比較表 → **B(子Source化しない)**

`商品／買掛金`のような簡略仕訳表記を含む、4方式×複数行の比較表(114ページ)。セル
単位に分割すると表全体の文脈を失うケース。

| 軸 | 評価 |
|---|---|
| 1. 意味的完結性 | **低い**。1セル単体(`商品／買掛金`)は、どの列(方式)・どの行(段階)に属するかという文脈なしには意味が確定しない |
| 2. 独立参照必要性 | **低い**。表全体または`parsed`内の行・列座標(例: `cells[1][2]`)で十分に一意な指定ができ、独立したContentBlockへの分割は不要 |
| 3. 文脈損失 | 高い。分割すると列見出しという文脈を失う |
| 4. 教材境界 | なし。セルの区切りはレイアウト境界であり、教材が意味的境界として明示しているわけではない |
| 5. 検出安定性 | 表構造の検出自体はレイアウト情報(座標)が必要(既存検証で確認済み)だが、これは粒度判断とは別問題 |
| 6. 重複許容可能性 | 該当なし |

**注目点**: B1と同型(軸1低い・軸2低い・軸3高い)のパターンで「不要」に到達して
おり、B1・B2の一致は判定軸の一貫性を裏付ける。

### C1. 電子記録債権の仕訳(1)(2) → **B(子Source化しない)**

同一論点「電子記録債権」の下に、`(1)取得時``(2)譲渡時`と番号付けされた、視覚的に
独立した2つの仕訳ボックス(52ページ、テーマ2-1、いずれのラベルにも属さずtopic
直下)。`(1)`は`×××`(金額)と`○○○`(勘定科目)のプレースホルダを含む。

| 軸 | 評価 |
|---|---|
| 1. 意味的完結性 | **高い**。ボックス全体(借方/貸方+プレースホルダ)で仕訳の型として意味が完結する |
| 2. 独立参照必要性 | **低い**。`(1)`(2)それぞれが既にトップレベルのContentBlockとして一意に参照可能であり、ボックス内部をさらに割る理由がない |
| 3. 文脈損失 | 高い。借方/貸方を割ると仕訳として不可分な構造が壊れる |
| 4. 教材境界 | `(1)`(2)という番号があるが、これは**ボックス同士を区切る境界**であり、**ボックス内部をさらに割る境界ではない** |
| 5. 検出安定性 | プレースホルダ検出はlayoutモード+`○`/`〇`両対応が前提(`pattern_detection_survey`3-3節)だが、検出できれば安定 |
| 6. 重複許容可能性 | 該当なし(分割しないため) |

**重要な発見**: A2と同じく「番号による教材明示境界」(軸4)があるにもかかわらず、
C1は「不要」と判定される。**軸4の有無だけでは A2 と C1 を区別できない。** 真の
違いは軸2(独立参照必要性)にある。A2の各脚注(`※1`〜`※5`)は互いに異なる算定内容
(取得原価の算定・按分計算等)を持ち、それぞれ独立して参照される可能性が高いのに
対し、C1の`(1)``(2)`は「同じ仕訳の異なる場面(取得時/譲渡時)」であり、**既に
それぞれが独立したトップレベルSource(兄弟関係)として扱われている**。これは
親子分割の対象ではなく、そもそも別々のStage1 Sourceである。**「教材上に番号
境界がある」ことは、それが「1つの親の内部をさらに割るべき境界」なのか「既に
並列した独立Source同士を区切る境界」なのかを区別しなければ、判定に使えない。**

### C2. 貸倒引当金差額補充法の反復計算 → **C(自動判断できずレビュー候補)**

`繰入額：貸倒見積高600－前T/B 400＝200`という具体的数値のみの計算が、4つの独立
した設例の解説内(93〜96ページ、テーマ5)にそれぞれ1回ずつ出現する。
`pattern_detection_survey.md`12節で確認したとおり、この計算パターンには**教材内で
明示された抽象定義ブロックが別途存在しない**(`○○○`のような一般化した式表現は
PDF原文に一度も現れず、常に具体的な数値のみで記載されている)。

| 軸 | 評価 |
|---|---|
| 1. 意味的完結性 | **高い**。計算式自体は具体的な数値のみで構成され、単体で意味が通る |
| 2. 独立参照必要性 | **不明瞭**。A1(定額法)と異なり、この計算パターンに対応する抽象定義ブロックが教材上どこにも存在しない。4つの解説それぞれが独立した計算に見えるが、これを「型の反復適用」として扱うべきか、単に「4つの独立した設例内計算」として扱うべきか、Parser単独では判断できない |
| 3. 文脈損失 | 中程度。解説の他の記述(貸倒引当金の残高等)と一定の関連はあるが、計算式自体は数値さえあれば意味が通る |
| 4. 教材境界 | なし |
| 5. 検出安定性 | 高い。具体数値のみのため、定額法のような分数・指数の崩れがなく抽出は安定している |
| 6. 重複許容可能性 | 該当する場合、子(計算行)は親(解説全文)に部分文字列として含まれる可能性が高い(A1と同様の扱いになりうる) |

**重要な発見**: A1との決定的な違いは軸2にある。A1は「抽象定義ブロックが別途
存在する」という教材上の事実があるからこそ、適用箇所を独立参照する意味
(role=applicationとして定義への参照を明確化する)が明確だった。C2はその
「参照先となる定義」自体が教材に存在しないため、**独立参照する意義そのものが
教材構造からは確定できない**。反復回数(4回)自体は判定に使わない方針だが、
「反復先の定義が存在するかどうか」という**構造的な事実**は、A1とC2を分ける
有効な観察材料になっている。

### C3. 定額法定義式・月割式・べき乗式の複数行分断 → **判定保留(検出前段階の問題)**

155ページの定額法定義式は、plainモードで9行以上に分断され、layoutモードでも
「分子側は1行に復元されるが分母は次の行に残る」という不完全な復元にとどまる
(`pattern_detection_survey.md`4-2節)。171〜174ページの月割計算(二重分数)では
layoutモードでも項が欠落する場合がある(同4-3節)。186ページのべき乗式では、
指数の数字が対象項の**前**の行に分断される(同4-4節、分数とは分断方向が逆)。

| 軸 | 評価 |
|---|---|
| 1〜4 | 未評価。理由は下記 |
| 5. 検出安定性 | **著しく低い**。単一行ベースの素朴なパターン検出器を使うと、1つの完結した式が抽出崩れによって複数の「候補行」であるかのように誤って検出されうる(例: 155ページで`（取得原価－残存価額）×`という行と`＝年間減価償却費`という行が、機械的には別々の候補に見えてしまう) |
| 6 | 未評価 |

**この検証で分かった重要な点**: このケースは「独立した複数候補をどう子Source化
するか」という本来の論点とは**性質が異なる**。実際にはこれは**単一の式**であり、
子Source化の必要性を論じる以前に、**Faithful Restoration段階での行結合・復元が
完了していなければ、そもそも「これが1つの候補なのか複数の候補なのか」を正しく
判定できない**、という**判定の前提条件**に関わる問題である。したがって
「C(レビュー候補)」に分類するが、その理由はA1・C2のような「独立性の判断が
本質的に難しいから」ではなく、**「判断そのものを行う前提(復元)がまだ満たされて
いないから」**という、性質の異なる保留である。

### C4. プレースホルダなしの具体的仕訳 → **B(子Source化しない)**

`(借) 費用勘定 1,200 (貸) 現金`のように、プレースホルダを一切含まない具体的な
仕訳(47〜48ページ、テーマ1、「参考」ラベル内)。

| 軸 | 評価 |
|---|---|
| 1. 意味的完結性 | **高い**。具体的な仕訳として単体で意味が完結する |
| 2. 独立参照必要性 | **低い**。仕訳ボックス自体が既にトップレベルの候補であり、内部をさらに割る理由がない(C1と同型) |
| 3. 文脈損失 | 高い。借方/貸方の構造は不可分 |
| 4. 教材境界 | なし |
| 5. 検出安定性 | 高い。具体数値+`(借)`/`(貸)`マーカーのみのため、`○○○`のような縦積み崩れの問題がない |
| 6. 重複許容可能性 | 該当なし |

**重要な発見**: C1(プレースホルダ付き)と全く同じ「B(不要)」判定に到達した。
これは、**プレースホルダの有無自体は、軸1〜6のいずれにも直接影響しない**ことを
示す。「プレースホルダ付きだから仕訳型として扱い、プレースホルダなしだから対象外」
という区別は、少なくとも**子Source化の必要性という観点では意味を持たない**。

---

## 6. 子Source化が必要だったケースの共通点

A1・A2を比較すると、両者に共通する唯一の条件は**軸2(独立参照必要性)が高いこと**
である。軸1(意味的完結性)・軸4(教材境界)は、A1では低い/なし、A2では高い/ありと
対照的であり、共通していない。

- **軸2が高い**ことが必要条件になっている可能性が高い。ただし軸2が高くなる理由は
  ケースによって異なる: A2は「教材が明示的に区切っているから」(軸4由来)、A1は
  「同じ`sourceBlockId`が2つの異なる意味(example/application)を同時に持って
  しまうから」(軸4なしでも成立する、role分離の必要性由来)。
- 軸6(重複許容可能性)は、A1・A2どちらも「既存方針(重複許容+`diag.provenance`+
  `relation`別gateChecks)で対応可能」という評価に落ち着いており、**重複が発生
  するかどうか自体は必要性判定の障害にならなかった**(重複が生じるA1も、生じない
  A2も、どちらも「必要」と判定された)。

---

## 7. 子Source化しなかったケースの共通点

B1・B2・C1・C4の4ケースに共通するのは**軸2(独立参照必要性)が低いこと**である。
軸1(意味的完結性)はB1・B2で低い、C1・C4で高いと分かれており、**軸1の高低は
「不要」判定を説明しない**。

- 軸2が低くなる理由も2パターンに分かれる。B1・B2は「分割すると文脈(依存関係・
  列見出し)を失うため、そもそも分割する意味がない」(軸3が高いことと表裏一体)。
  C1・C4は「対象は既にトップレベルのSourceとして独立しており、内部をこれ以上
  割る理由がない」(軸2が低い理由が軸3ではなく、対象の構造自体にある)。
- C1・C4は、教材上の番号・マーカー(軸4相当のもの)があってもなくても同じ「不要」
  判定に到達しており、**「独立した仕訳ボックスや計算ブロックそのもの」は、
  プレースホルダの有無や内部の番号付けに関わらず、それ自体が既にStage1の適切な
  単位であり、それ以上の子Source化を必要としない**、という傾向が観察された。

---

## 8. 自動判断が難しかったケース

- **C2(差額補充法の反復計算)**: 軸2の判定に必要な「参照先となる定義が教材上に
  存在するか」という事実自体が、A1(存在する)とC2(存在しない)で異なっていた。
  この事実そのものはParserが機械的に検出できる可能性がある(「同一パターンの
  計算式が複数箇所にあるが、それを一般化した用語ベースの定義ブロックが別途
  存在するかどうか」を確認する処理)。しかし、**その事実から「独立参照が必要か」
  を判断すること自体は、Derived Knowledge層の統合判断(既存設計4-2節でParserの
  責務外とされている領域)と重なる**ため、今回の検証範囲では「レビュー候補」に
  留めた。
- **C3(複数行分断される式)**: 「独立性の判断が難しい」のではなく、「判断の前提
  (Faithful Restorationによる復元)が満たされていない」という、性質の異なる
  保留。この2種類の「判断できない」を混同しないことが重要である(9節で扱う)。

---

## 9. 判定基準の暫定案(候補、確定ではない)

今回の8ケースの比較から見えてきた**候補**を示す。いずれも今回の限られたケース数
(8件)からの帰納であり、次フェーズでの追加検証を要する。

1. **軸2(独立参照必要性)が、他のどの軸よりも判定を分ける力が強かった**。軸1
   (意味的完結性)は「必要」「不要」どちらのケースにも高低が混在しており
   (A1は低いが必要、C1は高いが不要)、単独では判定を説明できない。
2. **軸4(教材明示境界)は、単独では十分条件にならない**。A2(必要)とC1(不要)は
   どちらも教材上の番号・記号境界を持つが結果が異なる。**境界が「1つの親の内部を
   さらに割るべき境界」なのか「既に並列した独立Source同士を区切る境界」なのかを
   区別する**必要がある。
3. **軸2が高くなる経路は少なくとも2つある**: (a) 教材が明示的に区切っており、
   各区切りが異なる意味内容を持つ場合(A2型)、(b) 教材の明示区切りがなくても、
   単一の`sourceBlockId`が複数の異なる意味(例: 事例そのものと、既存の型の適用)を
   同時に担ってしまい、それを分離する必要がある場合(A1型)。
4. **軸2が低くなる典型は、対象が既にトップレベルのSourceとして独立している場合**
   (C1・C4)。この場合、教材上の番号付けや内部のプレースホルダの有無は判定に
   影響しない。
5. **軸2の判定材料として、「反復パターンに対応する抽象定義ブロックが教材上に
   別途存在するか」という構造的事実が有効そうである**(A1 vs C2の対比)。ただし
   この事実の「有無の検出」と「そこから独立参照の要否を判断すること」は別処理
   であり、後者はDerived Knowledge層寄りの判断である可能性が高い。
6. **軸5(検出・復元の安定性)が著しく低い場合は、軸1〜4の評価より前に解決すべき
   前提条件の問題として切り分ける**(C3)。これを他の「レビュー候補」(C2のような
   意味的な保留)と同列に扱うと、レビューの目的が混同される。
7. **軸6(重複許容可能性)は、今回検証した範囲では常に「対応可能」だった**。重複が
   生じるかどうか自体は、必要性判定の直接の障害にはならなかった(既存方針で
   吸収できる範囲に収まっている)。

これらを組み合わせた**暫定的な判定の流れの候補**(あくまで候補、確定ルールでは
ない):

```
Step0: 軸5(検出・復元の安定性)が著しく低い場合 → 判定を保留し、Faithful
       Restorationの完了を待つ(C3型)。

Step1: 対象が既にトップレベルのSourceとして独立しているか(教材上の番号・
       記号が「兄弟を区切る境界」であって「内部を割る境界」でないか)を
       確認する → 独立している場合はB(不要)(C1・C4型)。

Step2: 軸2(独立参照必要性)を、次の観点から評価する。
       - 教材が明示的に区切っており、各区切りが異なる意味内容を持つか(A2型)
       - 単一の候補が複数の異なる意味(事例/型の適用等)を同時に担って
         しまっていないか(A1型)
       - 反復パターンに対応する抽象定義ブロックが教材上に別途存在するか
         (存在すればA1型に近づく、存在しなければC2型としてレビューへ)

Step3: 軸2が高いと判断できればA(必要)、低ければB(不要)、教材上の判断材料が
       不足していればC(レビュー候補)とする。
```

---

## 10. Parserで自動化できそうな範囲

- Step0(検出・復元の安定性チェック): `diag.extraction.artifacts`(`fraction_split`・
  `exponent_split`等)の有無を機械的に確認し、既知の崩れパターンが検出された場合は
  子Source化判定を一旦保留するというフラグ立ては自動化できそうである。
- Step1(トップレベル独立性の判定): 対象候補が、既に検出済みのStructureNode/ラベル
  境界と同じ階層に位置する独立した視覚単位(罫線・番号による区切り)かどうかは、
  既存のStructureNode認識・ラベル検出の出力と突き合わせることで機械的に判定できる
  可能性が高い。
- Step2の一部(「反復パターンに対応する抽象定義ブロックが別途存在するか」の**検出**
  そのもの): 同一・類似する用語構成のパターンが、ラベルなし・topic直下(定義らしき
  位置、7節の観察参照)に存在するかを機械的に確認することは可能そうである。ただし
  これは「存在の検出」までであり、「だから独立参照が必要」という判断そのものは
  次項の対象である。

## 11. 人間レビューへ送るべき範囲

- Step2の判断そのもの(「軸2が高いと言えるかどうか」の最終判定)。特にC2のように、
  反復パターンに対応する抽象定義ブロックが教材に存在しない場合、それを「型の
  反復」として扱うか「独立した複数の具体例」として扱うかは、教材の意図の理解を
  要する判断であり、機械的なルール化が難しい。
- A1型(単一候補が複数の意味を同時に担ってしまうケース)の判定。「この候補は
  `example`と`application`を両方担っているのではないか」という判断は、`role`
  概念そのもの(Parserの責務外、既存設計4-2節)と直結しており、Parser単体では
  最終判断できない。
- C3のような検出・復元不安定ケースの、復元完了後の再評価。

## 12. 既存Parser設計との整合性

- 今回の検証は、`parser_design_proposal.md`4節「Parser と Derived Knowledge の
  責務境界」で既に示されていた「Parserの責務は候補の提示までであり、確定的な
  意味分類(definition/application等)は次フェーズの責務」という整理と矛盾しない。
  9節の判定フロー案は、あくまで「独立Sourceとして切り出す候補にするかどうか」の
  一次判定であり、`role`の確定的な割り当ては引き続きDerived Knowledge層に委ねて
  いる。
- `parser_design_proposal.md`3-5節が保留していた「必要性判定基準」について、
  今回の検証は「記述的な基準(Derived Knowledgeから一意に参照する必要がある場合)」
  を、より具体的な複数軸の組み合わせへ分解する一歩になったと考えられるが、
  **正式なルールとして固定するにはケース数(8件)が少なく、本書1冊・限られた
  パターンの範囲での帰納である**ことに留意が必要である。
- 5-1節「親子Source間の`sourceFaithful`重複」の既存方針(重複許容+`diag.provenance`
  +`relation`別gateChecks)は、今回検証したA1・A2いずれのケースでも対応可能な
  範囲に収まっており、方針の見直しは不要と考えられる(6節)。
- C3で見つかった「検出前段階の問題」(Faithful Restorationの完了が子Source化
  判定の前提になる)は、`parser_design_proposal.md`1節のステージ順序
  ([4] Source Segmentation → [5] Faithful Restoration)と**一部矛盾する可能性が
  ある**。現在の設計は Source Segmentation(粒度確定)が Faithful Restoration
  (書き戻し)より先のステージとして位置づけられているが、今回の検証では
  「分数・指数を含む式について、Source Segmentationの判定(これは1つの候補か
  複数かの見極め)自体が、Faithful Restorationの復元結果に依存する」ことが
  示唆された。ステージ順序を変更すべきという結論ではなく、**この依存関係が
  実データで確認された**という事実を申し送る。

---

## 13. 次フェーズへの申し送り

- 8ケースというサンプル数は、判定基準を正式化するには少ない。特に「軸2が高く
  なる経路」(9節3項)が本当に2つ(A1型・A2型)に限られるのか、他の未検証パターン
  (例: `pattern_detection_survey.md`で確認した振出人/名宛人/指図人の3視点の仕訳
  (77ページ)、①②③という第三の列挙記号(92ページ)等)を追加で検証すると、更に
  別の経路が見つかる可能性がある。
- C3(検出前段階の問題)とC2(意味的な判断保留)という**性質の異なる2種類の
  「レビュー候補」**を同じ「C」ラベルで扱ってよいかは、次フェーズで再考の
  余地がある。少なくとも運用上は、「復元待ち」と「意味判断待ち」を区別できる
  形で要レビュー一覧に記録した方が、後続処理(または人間レビュー)が混乱しない
  と考えられる。
- 9節の判定フロー案(Step0〜3)は、次に「[7] Validation/DiagnosticsのgateChecks
  不変条件の具体化」を検証する際の土台として使える可能性がある。特にStep0
  (検出・復元の安定性チェック)は、gateChecksの不変条件候補(「`diag.extraction.
  artifacts`が存在する場合、対応する子Source化判定が保留状態になっているか」等)
  に転用できる可能性がある。
- 研究ブロック内部の➊➋とStructureNode候補との衝突(前回セッションで確認済み、
  87ページ)は、今回の検証対象(仕訳型・計算式・方程式パターン検出系)とは異なる
  StructureNode認識/ラベル検出間の衝突問題であり、本検証では扱っていない。
  別途の検証対象として残る。
- `diag`蓄積型設計の実装可能性確認は、今回明らかになった「Step0(復元安定性)の
  判定結果をどこに記録するか」という要件を踏まえて実施すると、より具体的な
  検証になると考えられる。
