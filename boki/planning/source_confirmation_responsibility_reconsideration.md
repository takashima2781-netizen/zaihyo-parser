# Source候補確定フェーズの責務再検討

ユーザーが実際に[8]候補確定フェーズをブラウザから操作した結果、
「この候補を独立Sourceとして確定すべきか」を判断する明確な基準がない、という
指摘を受けた。これは単なるUI説明不足ではなく、**人間に判断させる責務の
置き場所(レイヤー)自体が適切でない可能性がある**という問題提起である。

本ファイルは設計再検討の報告のみである。**コード変更・commit/pushには
一切進んでいない。** 新規実データ探索も行っていない(既存の定額法ケース
[定義Source1件+適用例2件]のみを対象とする)。

---

## 1. 前提として踏まえる既存設計

今回の再検討は、以前確立した以下の設計判断と矛盾しないことを必須条件とする。

### 1-1. C案(Parser設計v4)の到達点

`planning/stage3_c_plan_final_validation.md`・`planning/stage3_responsibility_
reconsideration.md`で、13ケース(仮想シナリオ)の分析を経て正式採用された
設計原則:

- Parserは**F群(機械的に確定できる事実)のみ**を出力する。F群はF1〜F8として
  棚卸し済み(検出の有無、境界記号、既存構造上の位置、Faithful Restoration
  状態、内容の空/非空、ネストの有無、構造的類似候補の有無、抽象定義候補の
  位置的存在)。
- **G群(独立参照必要性そのものの判断)は、Parserの責務から明確に除外する。**
  G群には「反復先定義候補との対応付けが正しいか」「境界形式と定義候補の
  有無が矛盾する場合にどちらを優先するか」「複数の表現が同一情報の言い換え
  かどうか」などが含まれる。
- 根拠として、D3(206ページ、仮想検証)のような反例が示された:
  「境界記号はあるが抽象定義候補が見つからない」という、F群同士が
  一見矛盾する事実が実際に存在し、**F群の組み合わせだけでは機械的に
  「必要/不要」を一意に決定できないケースがある**。

### 1-2. CLAUDE.md原則4(推測しない)

> 複数教材で同一の型・公式が確認できることは、その知識が本質的である
> ことを裏付ける有力な材料として扱ってよいが、それだけを理由に機械的に
> 「本質パターン」「応用パターン」を確定させる固定ルールにはしない。

この原則は、**反復・出現回数(F7・distinctThemes等)を根拠にした自動分類**
そのものを明確に戒めている。今回の再検討でも、この原則に抵触する自動化は
採用できない。

### 1-3. 今回の再検討がこの2つの原則と両立しなければならない理由

ユーザーの提案(「十分な構造的根拠があるものはParser側で自動確定する」)を
そのまま採用すると、**G群の判断をParser(または同等の機械的ロジック)に
持ち込むことになりかねない**。これは1-1節でせっかく分離したF群/G群の境界を
再び曖昧にするリスクがある。したがって、本検討の核心は「自動化してよい
範囲を、G群に踏み込まない形でどこまで狭く・具体的に定義できるか」である。

## 3. 「同一topic適用」と「テーマ横断適用」は質的に異なる

### 3-1. なぜ質的に異なるのか

- **`cand-topic-8-2-app`**: 候補の所属topic(topic-8-2)と、F8が指す定義
  Sourceの所属topic(topic-8-2)が**一致**する。これは「その論点自身が
  提示した定義式を、その論点自身の設例で使っている」という、教材の
  論点構成上ごく自然な状況であり、**「これは何の技術の適用か」という
  意味的な曖昧さがほぼ生じない**。判断材料としては、実質的に「同一
  StructureNode配下に、定義Sourceと同型のパターン候補が1つ存在する」
  という**位置関係の事実(F3+F8の組み合わせ)のみ**で説明が完結する。

- **`cand-topic-9-1-app`**: 候補の所属topic(topic-9-1、無形固定資産の
  ソフトウェア)と、F8が指す定義Sourceの所属topic(topic-8-2、有形固定
  資産の減価償却)が**一致しない**。これは「テーマ8で説明された技術が、
  テーマ9でも(教材上明示的な再定義なしに)再利用されている」という
  状況であり、**まさに原則4が名指しで警戒している「複数教材(今回は
  複数テーマ)にまたがる反復」そのもの**である。この場合、「本当に
  同じ技術の適用と扱ってよいか」は、位置関係の事実だけでは決定できない
  意味判断(G2・G4相当)を要する。

### 3-2. この区別はG群への踏み込みか

**踏み込まない。** 「候補の所属topicと、F8が指す定義Sourceの所属topicが
一致するかどうか」は、既存の構造情報(StructureNodeの階層、F8が既に
記録しているsourceBlockId)を突き合わせるだけで機械的に導出できる。
これは「独立参照が必要かどうか」という意味判断(G4)そのものではなく、
**「この候補と定義Sourceの位置関係」という、F3の精神をF8と組み合わせて
拡張した新しいF群項目(以下F9と呼ぶ)** と位置づけられる。

> **F9(新設)**: 候補の所属StructureNode(topic)と、F8が指す抽象定義
> 候補の所属StructureNodeが、祖先チェーン上で一致するか。

F9はF3(「既存の確定済み構造上のどの位置にあるか」)と同じ性質——**既存の
確定済み構造との突き合わせだけで機械的に判定でき、新しい教材が増えても
アルゴリズム自体は変わらない**——を持つ。これは1-1節が要求する「F群の
定義に踏みとどまっていること」を満たす。

### 3-3. F9だけで「自動確定してよい」と言い切れるか(反例チェック)

原則4・D3の教訓(反復の有無だけで機械的に断定しない)を踏まえ、F9が
成立する場合でも、以下の追加条件を満たさない限り自動確定の対象外とする。

1. **F8の一意性**: 候補のtopic内(またはその祖先)に、抽象定義候補が
   複数存在する場合(例: 同一topicに定額法と定率法の定義式が両方ある場合)、
   F8がどちらを指しているかの対応付け自体がG群の判断になりうる。したがって
   **F8の一致先が一意に定まらない場合は自動確定しない**。
2. **F4(Restoration解決済み)**: 未解決のまま自動確定すると、誤った
   `sourceFaithful`をそのまま確定Sourceにしてしまうリスクがある。
3. **F2との無矛盾性**: D3のような「境界記号はあるのに定義候補がない」
   逆に「境界記号がないのに複数の異なる型が同居している」等、既存の
   F群同士が矛盾する兆候がある場合は自動確定しない(D3の教訓をそのまま
   踏襲する fail-closed 条件)。

これら3条件が揃わない限り原則`needs_review`へ回すため、**F9は「自動確定
してよい」ことの十分条件ではなく、「自動確定を検討する対象になりうる」
ための必要条件の1つに過ぎない**、という位置づけにする。

## 4. 7つの評価観点への回答

### (1) Parserが意味判断を再び抱え込むことにならないか

**抱え込まない、という設計は可能。** ただし条件がある。3-2節のF9は
「既存構造との突き合わせ」であり意味判断ではないが、**この判定を行う
主体をどこに置くか**は別問題である。Parser自身(`runApplicationCandidates.
mjs`)にF9の判定ロジックを実装すると、Parserの出力契約が「F群の事実の
記録」から「F群を用いた一次判定(自動確定/要レビューの振り分け)」へと
一歩踏み出すことになる。これは意味判断(G群)そのものではないが、
**Parserの責務が「事実の記録のみ」から「事実に基づく振り分け」へ
広がる**という点で、1-1節の原則(Parserは候補提示までで、判断は行わない)
の**字義どおりの解釈からは逸脱する**。

この逸脱を許容するかどうかは設計判断であり、8節で選択肢として提示する。
**本ファイルでは、F9の判定ロジック自体はParserの外側(候補確定フェーズを
担う後続処理、またはDK層側の統合処理)に置くことを推奨する**。Parserは
F1〜F9の事実をすべて記録して候補一覧レポートへ渡すところまでとし、
「F9が成立するので自動確定する」という**振り分けの実行**は、C案が
既に「[8]候補確定フェーズ」として明示的にParser外に置いていた工程の
内部で行う。これにより、Parser自体の出力契約は一切変更せずに済む。

### (2) F群の構造的事実だけで自動確定できる範囲をどこまで定義できるか

3-2節・3-3節のとおり、次の場合に限定する。

```
F9(候補のtopicとF8定義Sourceのtopicが祖先チェーン上で一致) = true
かつ F8の一致先が一意
かつ F4(Restoration) = resolved:true
かつ F2とF8の間に矛盾がない
```

今回の2件では、`cand-topic-8-2-app`のみがこの条件を満たす。

### (3) 自動確定・needs_review・自動除外の3分類が成立するか

成立する。

| 分類 | 条件 | 今回の該当例 |
|---|---|---|
| 自動確定 | 2節の4条件をすべて満たす | `cand-topic-8-2-app` |
| needs_review | F1・F5等は満たすが2節の条件を満たさない(F9不成立・F8複数一致・F4未解決・F2矛盾のいずれか) | `cand-topic-9-1-app`(F9不成立、テーマ横断) |
| 自動除外 | F1が偽(パターン未検出)、またはF5が偽(内容が空) | 今回の2件には該当なし(D1の②③相当、既存のD1仮想検証で確認済みの分類) |

### (4) 今回の2件の適用例は、本当に自動確定できるケースなのか

**2件とも自動確定できるわけではない。** `cand-topic-8-2-app`(同一topic
適用)は2節の条件を満たし自動確定候補になりうるが、`cand-topic-9-1-app`
(テーマ横断適用)は原則4が名指しで戒めている「複数テーマにまたがる反復」
そのものであり、**自動確定の対象にはならない**。むしろこちらこそ、
3軸モデルの`distinctThemes`・`crossesBaseAdvanced`が可視化しようとして
いる「テーマを越えた本質性の証拠」であり、**人間が最も注意深く見るべき
候補**である。

### (5) Sourceを自動確定した後、Derived Knowledge側で人間が確認すれば安全性・監査可能性を維持できるか

**現行実装のままでは維持できない。** 実際に今回、ユーザーが2件とも
確定操作を行った結果を確認したところ、**`reviewStatus`は`"approved"`の
まま変化していなかった**(2節で後述する実例)。つまり、既に承認済みの
Knowledgeへ`sourceRefs`が2件追加されたにもかかわらず、「この状態の
Knowledgeを承認する」という人間の判断は一度も行われていない。これは
自動確定の有無にかかわらず、**現行の統合ロジック(`integrateApplication
Source.mjs`)自体が既に抱えている監査可能性の欠陥**であり、6節で詳述する。

安全性・監査可能性を維持するには、**「Sourceの確定」と「Knowledgeへの
統合」を、Knowledge側の再承認を必ず要求する形で連動させる**設計変更が
必要である(8節で詳述)。

### (6) 誤ったSourceが自動確定された場合でも、Knowledge生成・統合段階で止められる構造になっているか

**現行のsourceRefs構造では止められる。** `sourceRefs`はSourceへの参照
(`sourceBlockId`)であり、`content`(rawFormula/structure)には影響しない
(ユーザー承認済みの既存方針: 「definition由来のcontentをKnowledgeの正本
とし、application Sourceはsourceデータを増やすのではなくsourceRefsとして
追加する」)。したがって、誤って自動確定されたSourceが統合されても、
Knowledge本体の計算式(`content`)が壊れることはない。**壊れうるのは
`evidence`・`consolidation`の数値・状態のみ**であり、これは(5)の再承認
フローで人間が最終確認すれば、統合前に差し戻せる。

ただし、これは「(5)の再承認フローを実装した場合」の話であり、**現行の
まま(reviewStatusが変化しない)自動確定を追加すると、誤ったSourceの
統合がそのまま`approved-knowledge.json`(M5/M6が参照する公式データ)へ
無審査で反映されてしまう**。したがって(5)の是正は、自動確定を導入する
かどうかに関わらず、それ以前に必須の前提条件である。

### (7) 各既存設計要素への影響

| 対象 | 影響 |
|---|---|
| Parser設計v4(`parser_design_proposal.md`) | (1)の結論により**変更不要**。Parserの出力契約(F群のみ)はそのまま維持できる。F9はParser外(候補確定フェーズ)で計算する新しい派生事実として位置づける |
| gateChecks | 新設が必要。例: 「自動確定されたSourceの統合は、必ずKnowledgeのreviewStatusを非approved状態にすること」「F9の一意性条件を満たさない自動確定が発生していないこと」「confirmationMethod(auto/human_reviewed)が全candidateに記録されていること」 |
| Faithful Restoration | 影響なし。F4(resolved状態)を自動確定の必要条件として参照するのみで、Restoration自体のロジックは変更しない |
| 候補一覧レポート([7]) | 拡張が必要。F9(topic一致)・confirmationMethod(auto/human_reviewed/auto_excluded)を新しいフィールドとして追加する |
| [8]候補確定フェーズ | **役割が縮小する。** 全候補が人間の確認対象になるのではなく、2節の条件を満たさない候補(needs_review)のみが対象になる。また、そのレビュー画面自体をSource単位の独立ページから、Derived Knowledge側(M4拡張)の一部として提示する方向へ変更する(8節) |

## 5. 「この2回のSource確定操作を人間がやる必要があったのか」への回答

| 候補 | 今回人間が行った操作 | 新フローでの扱い | 人間の操作は必要だったか |

妥当性)とズレた形で提示されていた。**

## 6. 現行実装で新たに見つかった欠陥(自動確定の議論とは独立)

2節で触れたとおり、実データを確認した結果、**現行の`integrateApplication
Source.mjs`は、Sourceが(人間確定・自動確定いずれの経路であっても)
Knowledgeへ統合される際、`reviewStatus`を一切変更しない**ことが分かった。
これはPhase13実装時点で意図的な設計判断として明記していたもの
(「Source候補確定フェーズが、既にこの統合に対する人間のレビューを
担っている」という理由)だが、(5)の検証により、**この判断は前提が崩れて
いなくても、そもそも監査可能性の観点で不十分だった**ことが分かった。
Source確定という行為自体は「このSourceは実在し、内容は正しい」ことしか
保証しておらず、「このSourceを既存Knowledgeに統合してよいか」という
判断(G4相当)を兼ねているとは言えない。

**この欠陥は、自動確定を採用するかどうかに関わらず是正が必要である。**

## 7. 4案の比較

| 観点 | A. 現行維持(Source単位で毎回人間確定) | B. 原則自動確定＋例外のみ人間レビュー、レビュー地点はDK | C. 完全自動確定 | D. その他 |
|---|---|---|---|---|
| ユーザーの指摘への対応 | 対応しない。判断基準の不在・レビュー粒度のズレが残る | 対応する。基準は2節の条件で明示化され、レビューはKnowledgeの帰結という実際に問いたい内容に一致する | 対応するが、原則4への抵触リスクが残る | - |
| C案(Parser=F群のみ)との整合性 | 整合する(現状維持なので) | 整合する。自動判定ロジックをParser外(候補確定フェーズ)に置く限り、Parserの出力契約は不変 | **整合しない**。G4相当の判断を無条件に機械化することになり、C案が明示的に避けた領域に踏み込む | - |
| 原則4との整合性 | 整合する | 整合する。テーマ横断(F9不成立)は必ず人間レビューへ回すため、反復回数だけで機械的に断定しない | **抵触する**。テーマ横断の反復も無条件に自動確定すると、まさに原則4が禁じる「反復回数だけを理由にした機械的確定」になる | - |

| 運用コスト(将来8冊拡張時) | 高い。同一topic内の自明な適用ですら毎回クリックが必要になり、教材が増えるほど負荷が線形に増える | 中程度。自明なケースは自動化され、人間の労力はテーマ横断等の本当に判断を要するケースに集中する | 低い(が、上記2点のリスクを抱えたまま) | - |

### 7-1. 結論

**B案(原則自動確定＋例外のみ人間レビュー、レビュー地点はDerived
Knowledge)を推奨する。** ただし、ユーザーが提示した原案をそのまま
採用するのではなく、次の2点で範囲を絞り込む。

1. 自動確定の対象を、3-3節の4条件(F9一致・F8一意・F4解決済み・F2無矛盾)
   を満たす場合のみに限定する。特に**テーマ・topicをまたぐ反復は、
   原則4により自動確定の対象から明確に除外する**(F9が成立しない限り
   自動確定しない)。
2. 自動確定の判定ロジックは、Parser本体ではなく、Parser外(候補確定
   フェーズを担う処理)に置く。これによりParser設計v4・C案の出力契約
   (F群のみ)を一切変更せずに済む。

C案(完全自動確定)は、原則4への抵触・C案の責務境界からの逸脱という
2つの理由で明確に不採用とする。A案(現行維持)は安全側だが、ユーザーの
指摘した問題(判断基準の不在、運用コストの将来的な線形増加)を解決しない
ため、次善としても採用しない。

## 8. B案の詳細設計

### 8-1. なぜ変更すべきか

- 現行の[8]候補確定フェーズは、**F群だけで説明が完結する候補(同一topic
  適用)についても、人間に「独立Sourceとして確定すべきか」という抽象的な
  判断を求めており、実際には答えようのない質問になっていた**(ユーザーの
  実体験どおり)。
- 現行の統合ロジックは、Source確定操作を「Knowledgeへの統合を許可する
  人間の判断」と暗黙に同一視していたが、実際にはSource確定は「この
  Sourceの内容が正しいか」を確認しているに過ぎず、**「この統合によって
  Knowledgeの3軸状態(evidence/consolidation)が変化してよいか」という
  判断を代替できていなかった**(6節)。
- ユーザーが最終的に確認したいのは「教材から正しいKnowledgeや問題が
  作られているか」であり、Source単位のレビューはこの問いに対して
  粒度が細かすぎ、かつ判断材料が不足している。

### 8-2. どこまで自動化できるか

3-3節の4条件を満たす候補のみ。今回の実データでは`cand-topic-8-2-app`
(同一topic適用)のみが該当する。**この条件は意図的に狭い。** 今後
教材が増えた場合も、「同一topic内で、定義Sourceが一意に特定でき、
Restorationが完了している適用例」という、既存のF3・F8・F4をそのまま
再利用する範囲に留め、新しい種類の判断基準を追加しない。

### 8-3. どこに人間判断を残すべきか

- **needs_reviewとなった候補**(3-3節の条件を満たさないもの。今回は
  `cand-topic-9-1-app`)。
- **人間が確認する場所を、Source単位の独立ページから、Derived Knowledge
  側(M4拡張)へ移す。** 具体的には、`derivedKnowledgeCandidate`に
  `pendingSourceRefs`(未承認の追加候補、F群の事実付き)を持たせ、M4の
  画面に「この候補をKnowledgeへ追加してよいか」という形でF群の事実
  (parentContext・boundaryType・sameTypePatterns・F9の判定結果等)を
  添えて提示する。承認/却下は、既存のM4の`approve`/`reject`と同様の
  一方向の状態遷移として扱う。
- **自動確定された候補についても、統合の結果としてKnowledgeの
  reviewStatusが必ず非approved状態に戻り、人間の最終確認(再承認)を
  経由する。** これにより、自動確定はあくまで「Source候補の生成・確定
  作業を省略する」ものであり、「Knowledgeへの反映を無審査にする」もの
  ではない、という区別を維持する。

### 8-4. 既存設計のどこを変更する必要があるか

| 対象ファイル/設計 | 変更内容 |
|---|---|
| `output/cases/teigakuho-application.json`のスキーマ | 各candidateに`confirmationMethod: "auto" \| "human_reviewed" \| "excluded"`を追加。F9(topic一致判定)の結果を記録するフィールドを追加 |
| `src/parser/candidateActions.mjs` | 自動確定用の新関数(3-3節の4条件を評価し、満たせば`confirmed`へ即時遷移、満たさなければ`needs_review`相当の状態で待機)を追加。既存の人間による`confirmCandidate`/`rejectCandidate`はneeds_reviewの候補に対してのみ呼び出される形に変わる |
| `src/knowledge/integrateApplicationSource.mjs` | 統合時に`reviewStatus`/`reviewedAt`を必ずリセットする(現行の「変更しない」という設計判断を撤回する)。統合はKnowledgeに対して「pending」を作る操作に変わり、`approved-knowledge.json`への反映は人間の再承認を経由する |
| M4(`reviewActions.mjs`・`server.mjs`・`dev-viewer/index.html`) | `pendingSourceRefs`の表示・承認・却下を扱えるよう拡張。既存の`approve`/`edit`/`reject`に加え、pending追加分の個別承認/却下アクションが必要になる可能性がある(詳細設計は次フェーズ) |
| `dev-viewer/index.html`の「第2ケース: Source候補確定フェーズ」セクション | 役割が縮小し、**needs_reviewの候補のみ**を表示する形に変わる。自動確定された候補は、このセクションではなく、7節のセクション(M4拡張後のpendingSourceRefs表示)側に現れる |
| gateChecks | 新設(4節(7)参照) |
| Parser設計v4・候補一覧レポート | F9・confirmationMethodをF群の拡張項目として追記(Parser本体の出力契約自体は不変) |

### 8-5. 今回の2件が新フローでどう処理されるか(トレース)

```
[Parser] 候補検出(runApplicationCandidates.mjs、変更なし)
  → cand-topic-8-2-app: F1〜F8を記録
  → cand-topic-9-1-app: F1〜F8を記録

[候補確定フェーズ、新設のF9判定]
  → cand-topic-8-2-app:
      F9 = true(topic-8-2 = topic-8-2)
      F8一意 / F4 resolved / F2無矛盾 も満たす
      → confirmationMethod = "auto"、confirmationStatus = "confirmed" (即時)
  → cand-topic-9-1-app:
      F9 = false(topic-9-1 ≠ topic-8-2)
      → confirmationStatus = "needs_review"(人間の操作を待つ)

[Knowledge統合、reviewStatusリセットを伴う新integrateApplicationSource]
  → cand-topic-8-2-appの確定Sourceが、KnowledgeへpendingSourceRefsとして追加される
    (自動確定であっても、Knowledgeへの反映自体は保留状態で止まる)
  → reviewStatus: "approved" → "pending_review"(新設ステータス)へ遷移

[M4拡張画面(人間の操作)]
  → 表示内容:
     - 確定済み(自動): cand-topic-8-2-app由来のpendingSourceRef、
       F9等の判定根拠付きで「同一topic内の自明な適用として自動確定
       されました」と明示
     - 要レビュー: cand-topic-9-1-app、F群の事実(テーマ横断である
       ことを含む)付きで、まだSourceとしても確定していないことを明示
  → 人間は、cand-topic-9-1-appについて「これをテーマ9への追加適用例
    として認めるか」を判断し、認めればSource確定+Knowledge統合の両方が
    同時に実行される(却下すればSourceは`rejected`のまま、Knowledgeにも
    追加されない)
  → 最終的に、pendingSourceRefsが確定した内容でKnowledgeを再承認する
    (M4の既存approveアクションを、pending差分の反映込みで実行する形に拡張)
```

**今回すでに人間が行った2回の確定操作と比較すると**、新フローでは
人間の操作が「テーマ横断の1件をKnowledgeの追加適用例として認めるか」
という1回の、かつKnowledge視点での判断に集約される。同一topic内の
自明な適用(1件)については、操作そのものが発生しない。
