## ケース2: journal_pattern(fixed/placeholder/amountSlots)

対象: テーマ2「電子記録債権」(1)取得時・(2)譲渡時

```jsonc
// (1) 取得時
{
  "content": {
    "rawTemplate": "(借) 電子記録債権 ××× (貸) ○○○ ×××",
    "debitAccounts":  [ { "kind": "fixed", "value": "電子記録債権" } ],
    "creditAccounts": [ { "kind": "placeholder", "token": "○○○", "undetermined": "account_name" } ],
    "amountSlots":    [ { "token": "×××", "role": "amount" } ]
  }
}
// (2) 譲渡時
{
  "content": {
    "rawTemplate": "(借) 現金預金 ××× / 電子記録債権売却損 ××× (貸) 電子記録債権 ×××",
    "debitAccounts":  [ { "kind": "fixed", "value": "現金預金" },
                         { "kind": "fixed", "value": "電子記録債権売却損" } ],
    "creditAccounts": [ { "kind": "fixed", "value": "電子記録債権" } ],
    "amountSlots":    [ { "token": "×××", "role": "amount" } ]
  }
}
```

**確認したこと**: `debitAccounts`/`creditAccounts`の各要素は`kind`
フィールドを見るだけで「確定した科目名」か「科目自体が未定のプレース
ホルダ」かを、`○○○`という文字そのものを知らなくても判別できる
(`kind: "placeholder"`かつ`undetermined: "account_name"`という
フィールド名自体が意味を示している)。金額側は別配列
(`amountSlots`)にあり、`role: "amount"`という別の観点のラベルを
持つため、「科目が未定」と「金額が未定」という異なる種類の
不確かさが、構造上完全に別の場所に記録され、混同しない。

**評価: ①改訂案で自然に表現できた。前回の問題は解消した。**

## ケース3: calculation_formula(term/operator/fraction構造)

対象: テーマ8-2「減価償却」定額法

```jsonc
{
  "content": {
    "rawFormula": "（取得原価－残存価額）×（1年／耐用年数）＝年間減価償却費",
    "structure": {
      "kind": "sequence",
      "tokens": [
        { "kind": "term", "value": "取得原価" },
        { "kind": "operator", "value": "－" },
        { "kind": "term", "value": "残存価額" },
        { "kind": "operator", "value": "×" },
        { "kind": "fraction",
          "numerator":   [{ "kind": "term", "value": "1年" }],
          "denominator": [{ "kind": "term", "value": "耐用年数" }] },
        { "kind": "operator", "value": "＝" },
        { "kind": "term", "value": "年間減価償却費" }
      ]
    }
  }
}
```

**実際に「構造だけを読んで元の計算関係を再構成できるか」を試した**。
結果、**一意に読めなかった**。この`tokens`列を左から素直に読むと、
`取得原価－残存価額×（1年／耐用年数）`(＝取得原価から
「残存価額×按分率」を引く)とも解釈できてしまい、原文の意図である
`（取得原価－残存価額）×（1年／耐用年数）`(＝取得原価と残存価額の
差額に按分率を掛ける)と区別がつかない。**原文では丸括弧で明示されて
いた「（取得原価－残存価額）」というグルーピングが、term/operator/
fractionの3種類だけでは表現できていなかった。**

**最小限の追加提案**: `fraction`と同様の考え方で、`group`という
トークン種別を追加する(丸括弧によるグルーピングを表す。中に任意個の
トークン列を持てる)。

```jsonc
"tokens": [
  { "kind": "group", "tokens": [
      { "kind": "term", "value": "取得原価" },
      { "kind": "operator", "value": "－" },
      { "kind": "term", "value": "残存価額" }
  ]},
  { "kind": "operator", "value": "×" },
  { "kind": "fraction",
    "numerator":   [{ "kind": "term", "value": "1年" }],
    "denominator": [{ "kind": "term", "value": "耐用年数" }] },
  { "kind": "operator", "value": "＝" },
  { "kind": "term", "value": "年間減価償却費" }
]
```

この形であれば、「取得原価－残存価額」が先にグループ化されている
ことが構造から一意に読み取れ、`(取得原価－残存価額)×fraction`という
関係を誤りなく再構成できることを確認した。

**なお、`tokens`の読み方について前提を明確にする必要がある**:
グループで明示的に囲まれていない箇所(例: ケース5で確認する
「Ｘ－0.9Ｘ×fraction」)は、通常の数式と同じく**演算子の優先順位
(×・÷は－・＋より先に結合する)で読む**という規約を置くことで、
`group`を書かなくても正しく読める。`group`は「原文が丸括弧で
明示していて、かつ優先順位どおりに読むと原文と異なる結果になる箇所」
にのみ使う、という運用ルールとする。

**評価: ③最小限の追加変更が必要(`group`トークン種別の追加)。
前回の問題は一部解消(term/operator/fractionだけでは不十分と判明し、
`group`追加によって解消の見込みが立った)。**

## ケース5: solution_technique(steps + 指数の扱い)

対象: テーマ8、固定資産取得原価の逆算(建物: 分数を含む、備品: 指数を含む)

### 建物のケース(分数のみ、指数なし)

```jsonc
{
  "content": {
    "rawExample": "Ｘ－0.9Ｘ×（8年／30年）＝91,200 → Ｘ－0.24Ｘ＝91,200 → 0.76Ｘ＝91,200 → Ｘ＝120,000",
    "steps": [
      { "rawStep": "Ｘ－0.9Ｘ×（8年／30年）＝91,200" },
      { "rawStep": "Ｘ－0.24Ｘ＝91,200" },
      { "rawStep": "0.76Ｘ＝91,200" },
      { "rawStep": "Ｘ＝120,000" }
    ],
    "technique": "linear_equation_backsolve"
  }
}
```

`steps`配列に4段階の式変形を過不足なく記録できた。1段目
(`Ｘ－0.9Ｘ×（8年／30年）＝91,200`)は、ケース3で確認した「優先順位で
読む」規約により、`group`を使わなくても`Ｘ－(0.9Ｘ×fraction)`と正しく
読める(＝先に丸括弧で明示的にグルーピングされているのは分数部分のみで、
式全体の優先順位は通常の数式どおりのため)。**この点は①素直に入った。**

### 備品のケース(指数を含む)

原文の式は`Ｘ（１－0.20）の2年乗＝16,000`という、底(1－0.20)を2年分
累乗する式である。これを`term`/`operator`/`fraction`/`group`の
4種類のトークンだけで表現しようとしたが、**べき乗という関係を表す
手段が無く、表現できなかった**。

**最小限の追加提案**: `fraction`と対になる形で、`power`トークン種別を
追加する(`base`と`exponent`を持つ)。

```jsonc
"tokens": [
  { "kind": "term", "value": "Ｘ" },
  { "kind": "operator", "value": "×" },
  { "kind": "power",
    "base": [
      { "kind": "group", "tokens": [
          { "kind": "term", "value": "1" },
          { "kind": "operator", "value": "－" },
          { "kind": "term", "value": "0.20" }
      ]}
    ],
    "exponent": [ { "kind": "term", "value": "2年" } ]
  },
  { "kind": "operator", "value": "＝" },
  { "kind": "term", "value": "16,000" }
]
```

`group`と`power`を組み合わせることで、この式も過不足なく表現できる
ことを確認した。改訂案(第1弾)では「`power`が必要になるかどうかは
今後の教材で判断する」と保留していたが、**今回、本冊(No.1巻)の実データ
だけで既に必要であることが確定した**。

**評価: ③最小限の追加変更が必要(`power`トークン種別の追加。`group`は
ケース3で確認済みの追加を流用)。`steps`自体は①として機能した。
前回の問題は一部解消(複数ステップの保持は解消。指数を含む式の構造化は
`power`追加で解消の見込み)。**

## ケース4a: sourceRefs.role(definition/restatement/application/example)

対象: テーマ8-2(定額法の定義)、テーマ8の設例内の脚注(建物・備品への
数値適用)、テーマ9の設例内の脚注(ソフトウェア・コンピュータへの
数値適用)

```jsonc
{
  "knowledgeKind": "calculation_formula",
  "sourceRefs": [
    { "sourceBlockId": "block-8-2-definition",           "role": "definition" },
    { "sourceBlockId": "block-8-example-building-note2",  "role": "application" },
    { "sourceBlockId": "block-8-example-equipment-note2", "role": "application" },
    { "sourceBlockId": "block-9-example-software-note",   "role": "application" },
    { "sourceBlockId": "block-9-example-computer-note",   "role": "application" }
  ],
  "evidence": {
    "byRole": { "definition": 1, "application": 4 },
    "distinctThemes": ["theme-8", "theme-9"],
    "distinctBooks": ["book-1"],
    "crossesBaseAdvanced": false
  }
}
```

### 「1つのSourceが複数roleを同時に持つ可能性」について

実データで確認したところ、**本冊の該当箇所では、1つのSourceに複数の
roleが同時に必要になるケースは見つからなかった**。理由は、Source
ブロックの粒度を「`※1`・`※2`のような脚注単位」まで細かく分けている
場合、脚注1つ1つは「その論点の一般的な定義」か「特定の数値を当てはめた
適用」のどちらか一方に自然に定まり、両方に見えることはなかったため
(例: テーマ9の「※　20,000×1年／5年＝4,000」という脚注は、
数値を当てはめているだけの`application`以外の読み方をする余地が無い)。

ただし、これは**Sourceの粒度を脚注単位まで細かく保つことが前提**である
ことに注意が必要である。もし粒度を粗くし、「設例全体」を1つのSource
ブロックとして扱った場合は、その1ブロックが「一般的な知識の具体例として
の`example`」と「数値を当てはめた`application`」の両方に見える可能性が
高い(実際、`example`という語を用意した動機はこちらの粗い粒度を念頭に
置いていたと考えられる)。**今回は脚注単位の細かい粒度で検証したため
問題が顕在化しなかった**、という条件付きの結果であることを明記する。
`example`roleは、今回のような細かい粒度では出番が無く、より粗い粒度の
参照(例:「この設例全体が、この知識の理解を深める例になっている」と
いう緩い関連付け)を将来行う場合にのみ意味を持つ可能性がある。

`evidence.byRole`は`{definition: 1, application: 4}`として問題なく
集計できた。

**評価: ①改訂案で自然に表現できた(ただし脚注単位の粒度を前提とする、
という運用上の条件付き)。前回の問題は解消した。**

## ケース8: table構造と「／」

対象: (a) テーマ7、記帳方法比較表(分記法/売上原価対立法/二分法/三分法)、
(b) テーマ11、為替レート表記(「118円／ドル」等)

### (a) 比較表

```jsonc
{
  "blockKind": "table",
  "content": {
    "columnHeaders": ["分記法", "売上原価対立法", "二分法", "三分法"],
    "rowHeaders": ["期首T/B", "仕入", "売上", "決算整理前T/B", "決算整理", "決算整理後T/B"],
    "cells": [
      ["商品(期首試算表)", "商品(期首試算表)", "商品(期首試算表)", "繰越商品(期首試算表)"],
      ["商品／買掛金", "商品／買掛金", "商品／買掛金", "仕入／買掛金"],
      ["売掛金／商品・商品販売益", "売掛金／売上、売上原価／商品", "売掛金／売上", "売掛金／売上"],
      ["商品・商品販売益", "商品・売上・売上原価", "商品・売上", "繰越商品・売上・仕入"],
      ["仕訳なし", "仕訳なし", "売上原価／商品", "仕入／繰越商品、繰越商品／仕入"],
      ["商品・商品販売益", "商品・売上・売上原価", "商品・売上", "繰越商品・売上・仕入"]
    ]
  },
  "diag": { "note": "セル内の／は借方／貸方を区切る簡略仕訳表記(本表全体で共通)" }
}
```

行見出し・列見出し・6×4のセルという単純なグリッドで、実際の比較表の
内容を過不足なく保持できた。`diag`に表全体で1つの注記を置くだけで、
すべてのセル内の「／」の意味付けができた(セルごとの個別注記は不要
だった)。

### (b) 為替レート表記

「118円／ドル」は独立したブロックではなく、テーマ11の設例の問題文
プロパー文の一部(例:「商品100ドルを輸入し代金は掛とした（直物レート
118円／ドル）」)として出現する。改訂案の方針(4-B)どおり、**この
「／」に対して特別な構造化・解釈は一切行わず**、`worked_example`
ブロックの`sourceFaithful`(問題文全体)の中の、ただの地の文として
保持した。

`table`のセル(仕訳表記が期待される文脈)と、`worked_example`の問題文
プロパー文(仕訳表記が期待されない文脈)とで、同じ「／」という記号に
対する扱いが構造的に異なる(前者は`diag`で明示的に注記、後者は何も
しない)ことが、スキーマ変更なしに実現できることを確認した。**汎用の
スパン注釈が無くても、どちらの文脈でも誤解は生じない。**

**評価: ①改訂案で自然に表現できた(a・bとも)。前回の問題は解消した。**

## 総括

| ケース | 評価 | 前回の問題 |
|---|---|---|
| 2(journal_pattern) | ① | 解消した |
| 3(calculation_formula) | ③(`group`追加が必要) | 一部解消 |
| 5(solution_technique) | ③(`power`追加が必要。`group`はケース3と共用) | 一部解消 |

### 5ケースすべてについて改訂案が十分機能したか

**4ケース(2・4a・8)は改訂案どおりで十分機能した。2ケース(3・5)は
`structure.tokens`の語彙が`term`/`operator`/`fraction`の3種類だけでは
不足しており、`group`(丸括弧のグルーピング)と`power`(べき乗)という
2種類の追加が必要と判明した。**

### 追加修正が必要なら何か

`structure.tokens`のkind語彙へ`group`・`power`を追加する。加えて、
`group`で明示的に囲まれていないトークン列は「通常の数式と同じ演算子
優先順位で読む」という解釈規約を明文化する必要がある(この規約が
無いと、`group`をどこで使うべきかの判断基準が曖昧になる)。

### その修正は小規模か、モデルの再設計を要するか

**小規模である。** `structure.tokens`は改訂案(第1弾)の時点で
「トークン種別はopen vocabulary、将来`power`等を追加できる」と
明記しており、今回の追加(`group`・`power`)はまさにその想定どおりの
拡張にあたる。`fraction`と同じ「入れ子になれるトークン」という
既存パターンを踏襲しているため、`structure`全体の設計思想
(浅いトークン列・汎用ASTにしない)を変更する必要はない。

### Source/Derived Knowledgeモデルをこの時点で確定してよいか

**大枠(StructureNode/ContentBlock、4概念、3軸状態モデル、sourceRefsの
role、journal_patternのfixed/placeholder/amountSlots、tableの最小
グリッド構造)は、2回の検証を経て実データに対する破綻が見つからなく
なったため、確定してよい水準にあると考える。** `structure.tokens`の
kind語彙(`term`/`operator`/`fraction`/`group`/`power`)についても、
本冊(1冊)の範囲で実際に必要になったものはこれで出尽くしたと考えられる
(ただし No.2以降で新たな崩れ方が見つかれば、同じ仕組みで語彙を追加
すればよい、という前提)。

### Parser設計フェーズへ進んでよいか

**`group`・`power`の追加を改訂案(第1弾)へ反映したうえで、進んでよいと
考える。** 今回のように「机上の設計→小さな実データでの検証→最小限の
追加」というサイクルを2回繰り返した結果、追加の必要が小さくなって
きている(1回目は4項目の構造変更、2回目はトークン種別2つの追加のみ)。
これ以上、同じ規模の検証を重ねても得られる情報は逓減すると考えられる
ため、次はParser設計(教材構造分析からSourceを機械的に組み立てる部分の
設計)へ進むのが妥当だと考える。

なお、今回確認した`group`使用の運用ルール(明示的な丸括弧がある場合の
みグルーピングし、それ以外は演算子優先順位で読む)や、`sourceRefs.role`
が脚注単位の細かいSource粒度を前提としている、という点は、Parser設計
(=Source粒度をどこまで細かく分割するかの設計)に直接影響するため、
Parser設計の初期段階で明文化しておく必要がある。
