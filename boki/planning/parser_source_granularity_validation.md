# Source粒度 小規模実データ検証

`planning/parser_design_proposal.md`3節で提示したSource粒度の3候補
(案A: 視覚単位+アンカー参照 / 案B: 意味単位+親子関連付け / 案C: 教材明示境界
基準)について、実データを使った小規模検証を行った結果である。

**本ファイルは検証結果の報告のみ。** Parser実装・スキーマのコード化・
Derived Knowledge生成ロジックの実装には一切進んでいない。
`parser_design_proposal.md`自体もまだ書き換えていない。

## 検証の目的(再確認)

「Source粒度の唯一絶対のルールを決めること」が目的ではない。実データから
次を明らかにすることを目的とする。

- 基本となる分割単位
- 分割してはいけないケース
- 追加分割が必要になる条件
- 親子構造が必要か(必要な場合のみ・不要なら導入しない)
- Parserが自動判定できる境界 / 人間レビューが必要になる境界

3案は排他的な選択肢として扱わない。各ケースについて、次の段階的アプローチを
試し、どの段階で・どんな条件のときに次の段階へ進む必要が生じるかを確認する。

```
Stage 1: PDF上の視覚的完結単位を保持する(案Aの基本形)
   ↓ 教材自身が番号・記号で明示的に区切っている場合
Stage 2: その境界まで分割する(案C)
   ↓ Derived Knowledgeから一意に参照する必要があり、かつ
   ↓ Stage1/2の単位のままでは指し示せない場合
Stage 3: 意味単位の子Sourceへ分割し、親子関連付けを持たせる(案B)
```

各ケースについて、以下4軸で評価する。

- **A. Source Fidelity**: 教材上のまとまり・文脈・親子関係を失わず保持できるか
- **B. Knowledge Traceability**: `sourceRefs`(特に`role`)から根拠箇所を一意かつ
  自然に指せるか
- **C. Parser Feasibility**: その粒度をParserが現実的に生成できるか
  (人間の意味理解が必要な判断と、パターンマッチで済む判断を区別する)
- **D. Context Preservation**: 分割後も必要な周辺文脈へ戻れるか

併せて、その粒度で`extractionRaw`/`sourceFaithful`/`parsed`/`diag`が不自然な
重複なく保持できるかを確認する。

対象ケースは、これまでの調査・検証記録で既に問題が確認されている実例を中心に
選定した(新規のケース探索は最小限に留めた)。

## ケース1: 電子記録債権の複数仕訳(テーマ2、検証ケース2の粒度観点での再検証)

**教材の実態**: 同一論点「電子記録債権」の下に、「(1)取得時」「(2)譲渡時」と
番号付けされた、視覚的に独立した2つの仕訳ボックスが並ぶ。(1)は`×××`(金額)と
`○○○`(勘定科目)の両方のプレースホルダを含む。(2)は借方が複数行(現金預金/
電子記録債権売却損)にわたる。

**適用した段階**: Stage1で決着。各ボックスは既に視覚的に独立しており
(それぞれ罫線で囲まれた別個の図形要素)、かつ教材が`(1)`/`(2)`という番号で
明示的に区切っている(Stage2の条件も同時に満たす)。ボックス内部(借方/貸方の
複数行、プレースホルダ)をさらに分割する必要は生じない。**Stage3(親子構造)は
不要。**

| 軸 | 評価 |
|---|---|
| A. Fidelity | 高い。ボックス全体を1単位として保持することで、借方/貸方という不可分な仕訳パターンの構造が壊れない。プレースホルダの役割(amount/account)は`placeholders`配列で表現でき、ボックスを割らずに済む |
| B. Traceability | 高い。(1)(2)それぞれが独立した`journal_pattern`の`sourceRefs`として一意に参照できる。1ブロック=1roleで曖昧さが生じない |
| C. Feasibility | 中〜高。`(1)`/`(2)`という番号検出、`(借)`/`(貸)`という定型語+ボックス境界(罫線または空行)の検出は、ルールベースのパターン検出で対応できる範囲。ただし(2)で確認済みの「列入れ替わり」のような崩れ方は、ボックス境界の検出自体には影響しない(内容の抽出崩れの問題であり、粒度の問題ではない) |
| D. Context | 論点(StructureNode)の子としてボックスが並ぶ階層構造だけで、必要な文脈(どの論点の仕訳か)は保持される。追加の文脈参照は不要 |

**4概念モデル**: (2)の`extractionRaw`≠`sourceFaithful`(`column_order_shift`)
だが、これはボックス単位のまま扱えており、粒度とは独立した問題として処理できる。
親子構造がないため重複保存の懸念はない。

## ケース2: 定額法の定義と複数テーマでの適用(テーマ8-2→8/9、最重要ケース)

**教材の実態**: テーマ8-2で用語ベースの抽象式が1回だけ定義される。その後、
テーマ8内の複数設例(建物・備品)、テーマ9(ソフトウェア・社内利用コンピュータ)で、
**抽象式を再掲せず**、数値を当てはめた計算行(例:「取得原価20,000×1年／5年＝
4,000」のような形)が繰り返し現れる(4件以上)。この計算行は、各設例の解答部分の
中で、他の解説文とは視覚的に区別される独立した計算式の体裁(定義ブロックと同じ
「用語/数値+演算子」というパターン)で提示されている。

**適用した段階**: これが今回最も示唆に富むケースだった。

- 定義ブロック(テーマ8-2)自体はStage1で決着(1行の式、単独の視覚単位)。
- 各設例内の「数値適用箇所」は、**Stage2の対象ではない**(教材は`※1`のような
  明示的な番号でこの計算行を区切っていない。あくまで解答文の一部として自然に
  埋め込まれている)。しかし、**Stage3の条件(DKから一意に参照する必要がある)は
  満たされる**——設例全体を`sourceRefs`の対象にすると、後述のとおり`role`が
  `example`(この設例全体という意味)なのか`application`(定額法公式の適用と
  いう意味)なのか区別できなくなる。
- 一方で、この計算行自体は**定義ブロックの検出器と同じパターン検出器(漢字項+
  演算子)で機械的に検出できる**——つまり「教材が明示的に区切っていない」に
  もかかわらず、パターン検出器が独立した意味単位を見つけられるケースである。

**結論(重要な知見)**: 案Cは「教材が番号・記号で明示的に区切っている場合」を
条件としていたが、今回の検証で**それだけでは条件として狭すぎる**ことが分かった。
「教材の明示的区切り」に加えて、「**パターン検出器が独立して検出できる意味のある
構造要素(仕訳・計算式パターン)が、より大きな視覚単位の内部にネストしている
場合**」も、Stage3(子Source化)を検討すべき条件として追加する必要がある。

**採用した表現**: 設例全体を親ContentBlock(`worked_example`)として保持しつつ、
その内部で検出された計算行を子ContentBlock(`formula_termbased`、親への参照
`parentBlockId`を持つ)として登録する、**親子構造**を試した。

| 軸 | 評価 |
|---|---|
| A. Fidelity | 親: 設例全体(問題文+解答手順)がひとまとまりで保持され、高い。子: 計算行自体も文字どおり忠実に保持され、高い。ただし子単体は「取得原価20,000×1年／5年＝4,000」のような形式で、**単独では何の計算か分からない**(取得原価が何の資産か、という前提情報は親の文脈にしかない)——これはA軸というよりD軸の課題として現れた |
| B. Traceability | 子Source化することで初めて`role: application`が計算行そのものを一意に指せるようになった。もし設例全体しか参照できなければ、`role: example`(この設例という事例)と`role: application`(公式の適用箇所)が同一の`sourceBlockId`を指すことになり、区別する意味が失われる。**この検証により、`sourceRefs.role`の`application`と`example`が実データ上で区別可能な概念であるためには、この粒度の子Source化が前提になる**、ということが明確になった(設計案10節で保留になっていた論点への具体的な手がかり) |
| C. Feasibility | 検出そのもの(計算行のパターンマッチ)は定義ブロックと同じ検出器の再利用で対応でき、実現性は中〜高。ただし「この計算行が**どの定義済み公式の適用であるか**」の対応付けは、パターン一致(同じ演算子・似た用語構成)だけでは確証が持てず、**高度な意味理解に近い判断**になる。Parserの責務としては「計算行が検出された」という事実と、参考情報(近い用語構成の既存公式候補)までに留め、**「テーマ8-2の定義の適用である」という確定的な対応付けは、Derived Knowledge生成フェーズの判断に委ねる**のが妥当と考えられる |
| D. Context | 子は親設例への明示的な参照(`parentBlockId`等)を必ず持たせる必要がある。この参照がないと、子の`sourceFaithful`だけでは意味が再構成できない(上記A軸の指摘と表裏一体) |

**4概念モデル**: 子の`sourceFaithful`(計算行)は、親の`sourceFaithful`(設例
全体の文章)の**一部として文字面上重複する**(親の全文の中に子の文字列が
そのまま含まれる)。完全な二重管理ではない(親は設例全体、子は特定の1行のみ)が、
**同じ文字列が親・子2箇所に存在する**という構造になる。これは原文性そのものを
損なうものではないが、後述の「総括」で編集・保守上の注意点として扱う。

## ケース3: 固定資産買換・脚注を複数含む仕訳ボックス(テーマ8)

**教材の実態**: 借方・貸方が複数行にわたり、`※1`〜`※5`のように複数の脚注付き
補足式が1つの仕訳ボックスにぶら下がる、より複雑な型(調査レポート3節)。各脚注は
それ自体が短い算定式(取得原価の算定等)を含む場合がある。

**適用した段階**: Stage2で決着。教材自身が`※1`〜`※5`という記号で**明示的に**
区切っている(案Cの条件に正確に一致する)。ボックス本体(借方/貸方のテンプレート
部分)を親、各脚注を子とする**親子構造**を試した。

| 軸 | 評価 |
|---|---|
| A. Fidelity | 高い。ボックス本体は仕訳パターンとして不可分な形のまま保持され、各脚注もそれぞれ独立した算定内容として保持される。ボックスと脚注をどちらも崩さず両立できた |
| B. Traceability | 高い。ボックス本体への参照(`journal_pattern`)と、個々の脚注への参照(それぞれ独立した`calculation_formula`または`note`候補)が、`sourceRefs`上で明確に分離できる。ケース2と異なり、脚注は元々独立した番号を持つため`role`の曖昧さも生じない |
| C. Feasibility | 高い。`※1`〜`※5`という記号自体がテキストとして機械的に検出可能であり、これを境界とする分割はルールベースで対応できる。ケース2(パターン検出器頼み)より確実性が高い |
| D. Context | 脚注は「どのボックスの脚注か」という関係を明示的に保持する必要がある(`parentBlockId`相当)。ボックス本体側にも`(※1)`という参照記号がインライン表記として自然に含まれるため、双方向の対応関係は教材の表記からそのまま拾える |

**4概念モデル**: ボックス本体の`sourceFaithful`にはインラインの`※1`等の記号が
含まれるが、脚注の実体(算定内容)はボックス本体のテキストには含まれない(脚注は
ボックスの外側、別の場所に記載されている)。**ケース2と異なり、親子間で
`sourceFaithful`の文字面が重複しない**——脚注記号(ポインタ)と脚注本体
(実体)が教材の時点で既に分離されているため、Sourceの分割がその構造をそのまま
写し取るだけで済む。

## ケース4: 記帳方法比較表(テーマ7)

**教材の実態**: `商品／買掛金`のような簡略仕訳表記を含む、4方式×複数行の比較表。

**適用した段階**: Stage1で決着。表全体を1つの視覚的完結単位として保持する。
**セル単位への分割(Stage3相当)は試みたが、採用しなかった。**

セル単位に分割した場合の具体的な問題: 1つのセル(`商品／買掛金`)の中の「／」が
借方/貸方の区切りという意味を持つと判定するには、**そのセルがどの列(方式)・
どの行(段階)に属するかという文脈が不可欠**であり、セル単体は自己完結しない。
分割してもセルの集合(結局は表全体)をまとめて参照する仕組みが別途必要になり、
分割した意味が失われる。

| 軸 | 評価 |
|---|---|
| A. Fidelity | 表全体を1ブロックにすることで、行見出し・列見出し・セルの関係が`parsed`の2次元グリッド構造としてそのまま保持される。セル分割案では逆にこの関係が壊れていた |
| B. Traceability | 表そのものをDerived Knowledgeの対象にする想定は薄いが(SPEC.md、型/公式が対象)、仮に参照する場合も表全体または`parsed`内の行・列座標(例: `cells[1][2]`)で十分に一意な指定ができ、独立したContentBlockへの分割は不要だった |
| C. Feasibility | 表の境界検出(罫線・列位置の認識)自体は、単純なテキストパターンより難易度が高く、レイアウト情報(座標)が必要になる可能性がある。ただしこれは「粒度の判断」の難しさではなく「抽出そのもの」の難しさであり、8節で別途検証が必要な事項として整理する |
| D. Context | 表全体を1ブロックにする設計そのものが文脈保持を担保する。分割しないことが最善の文脈保持策になっている、数少ない逆転ケース |

**4概念モデル**: `sourceFaithful`は表全体の忠実なテキスト、`parsed`が
行見出し/列見出し/セルのグリッド(設計案3節で既に確定済みの構造)。親子構造は
不要で、単一ブロック+内部構造という組み合わせが最も自然だった。

## ケース5: 分数を含む算定式(定額法公式そのもの、4概念モデル中心の確認)

**教材の実態**: `pdftotext`により分数の分子・分母が別行に分離する崩れ
(調査レポート9節・検証ケース3)。ケース2の「定義ブロック」と対象は同じだが、
ここでは粒度そのものより**4概念モデルの各段階との整合**を主目的に確認する。

**適用した段階**: Stage1で決着(1つの完結した式=1ContentBlock)。分数の崩れに
引きずられてトークン単位・行単位に分割することはしない——分割すると「1つの
完結した式」という原文の忠実な単位(要約・言い換え禁止の原則)が壊れる。

| 軸 | 評価 |
|---|---|
| A. Fidelity | 崩れた見た目(`extractionRaw`)に関わらず、書き戻し後の1つの完結した式(`sourceFaithful`)を単位とすることで、原文の意味的なまとまりが保たれる |
| B. Traceability | 定義ブロックとして単独で参照可能。ケース2で述べた「適用箇所」からこの定義ブロックへの逆参照(「この計算はこの定義の適用である」という対応付け)は、教材が明示していない限りSource層では持たせない(原則6、教材に書かれていない類似性を推測しない) |
| C. Feasibility | 分数の分断パターン(`fraction_split`)は既に複数箇所で確認済みの既知artifactであり、検出(異常のフラグ立て)は自動化しやすい。書き戻し自体は5-1節の方針どおり当面人間確認を必須とする |
| D. Context | 式単体で意味が完結しており、追加の文脈参照は不要 |

**4概念モデル**: `extractionRaw`(分断された生テキスト)→`sourceFaithful`
(書き戻した1行の式)→`diag.extraction.artifacts = ["fraction_split"]`という
経路が、粒度を1ブロックに保つことで問題なく機能した。これは前回の検証
(book1_prototype_validation_results.md ケース3)と同じ結論の再確認であり、
今回新たな問題は見つからなかった。

## ケース6: 方程式解法(単一記号Ｘ、指数を含む複数ステップ)

**教材の実態**: `Ｘ－0.24Ｘ＝91,200 → 0.76Ｘ＝91,200 → Ｘ＝120,000`のような、
複数ステップにわたる式変形。分数・指数の両方の抽出崩れが同時に発生する実例。

**適用した段階**: Stage1で決着。**ステップごとに別ContentBlockへ分割することは
しない。**

理由: 各ステップは前のステップからの導出であり、順序・依存関係を持つ。ステップを
独立したContentBlockに分割すると、「ステップ2単体」を指す参照が可能になって
しまうが、それを指す実用的な理由がない(ステップ2は文脈上ステップ1に依存して
初めて意味を持つ)。複数ステップの構造化は、ContentBlockの分割ではなく、
**1ブロックの`parsed`内部に`steps`配列を持たせる**(前回検証で既に提案されて
いる対応)ことで解決すべき問題であり、Source粒度の論点ではなくParsing段階
(6節)の`parsed`構造の論点であることを、今回改めて切り分けて確認できた。

| 軸 | 評価 |
|---|---|
| A. Fidelity | 1ブロックに保つことで式変形の連続性(導出の流れ)が保たれる |
| B. Traceability | `solution_technique`として1件の`sourceRefs`で参照でき、曖昧さはない |
| C. Feasibility | 複数行にまたがる式変形をひとつの範囲として認識する処理(開始行〜終了行の判定)は、単一式の検出より難易度が上がる。ただし境界自体は「Ｘという記号の出現から、最終行の数値確定まで」という比較的明確なパターンで捉えられる可能性がある(要検証、8節) |
| D. Context | ブロック内で完結しており、外部文脈への依存はない |

**4概念モデル**: `diag.extraction.artifacts`に`fraction_split`と
`exponent_split`が同時に入る(配列であることの効果を実データで確認済み、前回
検証の再確認)。粒度を1ブロックに保つことで、複数種のartifactを1つの
`diag`にまとめて記録でき、複雑にならなかった。

## ケース7(追加): 設例→解説の対提示(基準ケース)

**選定理由**: これまでのケースはいずれも何らかの複雑さを含む実例だった。
教材で最も高頻度(設例61件・解説57件、全テーマに分布)な「ごく普通の設例→解説の
対提示」に対して、今回検討した段階的アプローチが**不必要な複雑さを強制して
いないか**を確認する必要があると考え追加した。

**教材の実態**: 特に脚注・数値適用・複雑な仕訳を伴わない、通常の設例(問題文+
数値)とその解説(解答手順の説明文)の対。

**適用した段階**: Stage1のみで完全に決着。設例=1ContentBlock
(`worked_example`)、解説=1ContentBlock(`explanation`)、同じStructureNodeの
子として並ぶ。子Source化の判断(ケース2で必要になった条件=内部にパターン
検出可能な計算式がネストしているか)は、このケースでは該当しない(該当する
計算式が無いか、あっても定義済み公式の再掲ではなく単発の計算)ため、Stage3へ
進む必要が生じない。

| 軸 | 評価 |
|---|---|
| A〜D | いずれも高い評価。特別な処理を要さず、Stage1のみで4軸すべてが素直に満たされた |

**確認できたこと**: ケース2で見つかった「Stage3が必要になる条件」
(パターン検出器が検出できる意味単位が内部にネストしている場合)は、**該当しない
限り発動しない条件付きの追加処理**であることが、この基準ケースとの対比で
確認できた。多数派(基準ケース)には複雑な機構を強制しない、という設計方針が
実データ上も成立している。

## 総括

### 基本となる分割単位

**教材が視覚的に提示する完結単位(Stage1)を既定の分割単位とする。** 仕訳
ボックス1つ、式1行(または1つの完結した式変形)、設例1つ、解説1つ、参考/
留意点/コラム1つ、表全体1つ、が基本単位になる。7ケース中、5ケース
(1・4・5・6・7)がStage1のみで決着した。

### 分割してはいけないケース

- **表のセル**(ケース4): 文脈(列見出し=方式)を失う。
- **複数ステップの式変形**(ケース6): 逐次的な依存関係を失う。ステップの
  構造化は`parsed`内部で行うべきであり、ContentBlockの分割問題ではない。
- **仕訳ボックスの借方/貸方**(ケース1・3): 1つの仕訳パターンとして不可分。

### 追加分割が必要になる条件

2つの異なる条件が見つかった。

1. **教材が番号・記号で明示的に区切っている場合**(案C、ケース3の`※1`〜`※5`)。
   この条件は当初の想定どおり機能し、判定も比較的容易(記号の機械的検出で足りる)。
2. **(今回新たに確認)教材は明示的に区切っていないが、より大きな視覚単位の
   内部に、パターン検出器が独立して検出できる意味のある構造要素(仕訳・計算式
   パターン)がネストしている場合**(ケース2、設例内の数値適用箇所)。この条件は
   案Cの想定より広く、`parser_design_proposal.md`の3-4節時点では明示的に
   カバーされていなかった。

### 親子構造が必要か

**条件付きで必要、ただし全ケースに一律導入すべきではない。** 7ケース中、
親子構造が実際に機能したのはケース2・3の2件のみ(いずれも上記「追加分割が
必要になる条件」のいずれかに該当するケース)。ケース1・4・6・7では親子構造は
不要どころか、導入すると文脈やまとまりを損なう方向に働く。**「親Source=
視覚的完結単位を保持しつつ、上記2条件のいずれかに該当する場合にのみ子Source
を生成する」という条件付きの2階層モデル**が、今回の検証範囲では最も無理が
少なかった。

### Parserが自動判定できる境界 / 人間レビューが必要になる境界

| 判定内容 | 難易度 |
|---|---|
| 仕訳ボックスの境界(`(借)`/`(貸)`+罫線・番号) | 自動判定可能(ルールベース) |
| `※N`等、教材明示の脚注記号 | 自動判定可能(ルールベース、確実性が高い) |
| 用語ベース計算式・方程式のパターン検出(「ここに式がある」という検出自体) | 自動判定可能(パターンマッチ) |
| 表の境界(罫線・列位置) | 自動判定の難易度は中程度、レイアウト情報が必要になる可能性(要追加検証) |
| 複数ステップの式変形の開始/終了行 | 自動判定の難易度は中程度(要追加検証) |
| 「検出された計算式が、どの定義済み公式の適用であるか」の対応付け | **人間レビューが必要**(または少なくともDerived Knowledge生成フェーズの責務。Parserは「検出された」という事実の提示に留める) |
| Q&A等アイコンのみブロックの存在検出そのもの | **人間レビューが必要**(既存の結論を維持、テキスト上の手がかりが原理的に無い) |

### 4概念モデルへの影響・新たな注意点

親子構造を採用したケース(2・3)のうち、**ケース2でのみ**親子間で
`sourceFaithful`の文字面が部分的に重複する(子の内容が親の全文に含まれる)
ことを確認した。ケース3では脚注記号(ポインタ)と脚注本体(実体)が教材の時点で
既に分離されているため重複は生じなかった。

この重複は原文性そのものを損なうものではないが、**同じ内容を2箇所で保守する
必要が生じるリスク**がある。対応案として「子の`sourceFaithful`を親への範囲
参照(span)にする」ことも考えられるが、これは設計案7-7節で明確に否定した
「汎用スパン注釈の導入」に抵触しかねない(あちらは記号の意味解釈のためのスパン
注釈だったが、メカニズムとしては同種になる)。**この矛盾をどう解消するか
(重複保存を許容する/限定的なスパン参照を認める/ケースバイケースで判断する)は、
今回決定せず未決事項とする。**

## この検証で決定した(と言える)こと・決定していないこと

**決定した(実データで裏付けが取れた)こと**

- 基本分割単位はStage1(視覚的完結単位)。
- 案A/B/Cは排他的でなく、条件によって組み合わせる。
- 親子構造は必要になるケースが実在するが、全ケースに一律適用すべきではない。
- 案Cの「教材明示境界」条件だけでは、子Source化が必要なケース(ケース2)を
  カバーしきれない。パターン検出器によるネスト検出という条件を追加で
  考慮する必要がある。

**決定していない(次の判断が必要な)こと**

- 親子構造の具体的なフィールド設計(`parentBlockId`という名称・形は今回の
  検証のための仮の表現であり、確定していない)。
- 親子間の`sourceFaithful`重複をどう扱うか(上記のとおり)。
- 「パターン検出器がネストした構造を検出した」ことと「それが特定の定義済み
  公式の適用である」ことの対応付けを、Source層・Derived Knowledge層のどちらの
  責務にどこまで割り振るか(今回は「検出はSource層、確定的な対応付けはDK層」と
  仮に切り分けたが、これは提案であり確定ではない)。
- 表・複数ステップ式変形の境界検出の実際の自動化難易度(要追加検証、
  `parser_design_proposal.md`8節から持ち越し)。
