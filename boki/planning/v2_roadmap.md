CLAUDE.md「v1完成」節に記録済み。要約:

④依存関係 ⑤実装規模の概算 ⑥時期の見立て、を整理する。

  広げる最も手戻りの少ない作業(既にSource/Knowledge候補は生成済みで、
  承認するだけで学習内容が増える)。
- **長期ビジョンへの重要度**: 低〜中(単一教材内のコンテンツ量の話であり、
  アーキテクチャの汎用性検証には寄与しない)。
- **依存関係**: なし(独立)。ただし2-8(Knowledgeの同一性判断の遡及適用)
  と合わせて整理すると効率が良い。
- **実装規模**: 小(分類ロジック+ユーザー提示のみ。承認自体は

### 2-5. 複数教材・複数科目への対応

- **解決すること**: 長期ビジョンの中核(財表以外の科目・教材も同じ仕組みで
  投入できることの実証)。
- **今やる価値**: 低〜中(v1は「教材理解・変換エンジンが科目非依存に設計
  されている」ことまでは確認したが、**実際に2科目目を投入して初めて
  実証できる**)。
- **長期ビジョンへの重要度**: 最重要(北極星そのもの)。
- **依存関係**: 2-4(1データセット制約)の解決、または「解決しなくても
  ファイル切替運用で許容する」という判断のいずれかが前提。
- **実装規模**: 大(新科目のドメイン調査・Parser設計から。CLAUDE.md原則6

  を最初に実証する機会でもある)。
- **長期ビジョンへの重要度**: 高(「Knowledgeに適したExerciseを生成する」

- **依存関係**: なし(既存の`exerciseGeneratorRegistry.mjs`

## 3. 段階分け案

「改善を続けていたらいつまでも完成しない」状態を避けるため、それぞれに
**有限な終了条件**を持つ3段階を提案する。

### v1.1(規模小・リスク低、着手障壁が無いもの)

**目的**: v1で証明したend-to-endを壊さず、既存データ・既存UIの整理と
実運用フィードバックの収集を行う。新しいアーキテクチャ要素は増やさない。

含む候補: 2-10(実運用フィードバック、最優先)・2-1(49件の機械的整理)・
2-9(レビューUI改善)・2-11(技術的負債の解消)・2-12(learning-ui整理)。
2-2/2-3は判断待ちのまま並行してよい(ブロッカーにしない)。

**終了条件案**:
1. 財表ドリルでboki-app生成のExerciseを実際に一定期間(例: 1週間程度)
   使ってみたフィードバックが得られている
2. 未承認49件が「機械的に安全」/「要判断」に分離され、要判断分のみが
   ユーザーに提示されている
3. `checkDuplicateSourceFaithful`が新しい同一性判断の原則と整合している
4. v1のend-to-end(定額法+journal_pattern6件)が壊れていない(regression
   なし)

### v1.2(Exercise種類の拡張、教材内容の拡充)

**目的**: 「同じKnowledgeを複数のアウトプット方法で学習する」という長期
ビジョンの一部を、財表という同じ教材の範囲内で初めて実証する。

含む候補: 2-6(穴埋め形式Exerciseの追加)・2-2/2-3(判断が付いていれば
実装)・49件のうち承認されたものの投入。

**終了条件案**:
1. 並べ替え以外の出題形式(穴埋め)が、承認済みKnowledgeから少なくとも
   1件生成され、財表ドリルで実機確認されている
2. v1.1同様、既存end-to-endにregressionがない

### v2(複数科目対応の土台、アーキテクチャの本当の検証)

**目的**: 「boki-appの設計が本当に科目非依存か」を、2科目目の実投入で
検証する。長期ビジョンの中核。

含む候補: 2-4(1データセット制約の解消、財表ドリル側との協議が前提)・
2-5(2科目目の投入)。

**終了条件案**:
1. 財表・簿記論以外の2科目目(具体的な科目はユーザーが選定)について、
   教材投入 → Source → Knowledge → Exercise → Exercise View → 学習エンジン
   → 回答・採点・履歴、のend-to-endが実データで確認できている
2. 学習エンジン側で、財表・簿記論・2科目目が(併存または合理的な切替
   方式のいずれかで)実用上問題なく扱える

### v3以降(時期尚早、今回は規模見積りのみ)

2-7(問題集対応)・2-8(教材追加作業の自動化)。いずれも複数科目投入の
実績が積み上がってから、実データにもとづいて設計すべき(CLAUDE.md原則6)。

## 4. 推奨する次の一手

上記のとおり、**2-10(実際に日常学習で使ってみる)が、他のすべての優先
順位判断の前提になる**。次にどのフェーズへ進むかを決める前に、まず
財表ドリル上でboki-app生成のExerciseを実際に使ってみることを推奨する
(実装作業ではなく、ユーザー自身の利用体験)。そのうえで、v1.1の範囲・
優先順位を確定するのが合理的だと考える。
