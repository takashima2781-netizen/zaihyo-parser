`planning/stage3_responsibility_reconsideration.md`で評価したC案(Parserは候補
検出+構造的事実の提示までとし、子Source化の最終判断を別責務へ渡す)を前提に、
Parserパイプラインの責務境界を正式に整理した結果である。

**本ファイルは設計再整理の報告のみである。** 新規実データ探索・既存planning
文書の改訂・正式スキーマのコード化・Parser本体実装・`relation`モデルの拡張
には一切進んでいない。commit/pushも行っていない。D2の「本文個別仕訳と要約表」
のrelation問題は、7節でユーザー指示どおり明示的に未決事項として残し、今回は
解決しない。

## 1. C案前提のParserパイプライン再定義

既存7段階([1] Extraction 〜 [7] Validation/Diagnostics)の段階数・名称は
維持を前提にせず、責務が自然に分かれることを優先して再整理する。

### 1-1. 各段階の再定義

```
[1] Extraction ── 変更なし
     ページ単位の生テキスト取得(extractionRawの元)。意味解釈なし。

[2] Structure Recognition ── 変更なし
     StructureNode骨格(テーマ/論点/サブ項目)の確定。

[3] Block Detection ── 責務は維持、位置づけを明確化
     ラベル検出系・パターン検出系による候補の洗い出し。既存1-2節の方針
     (「より大きな視覚単位の内部に対しても同じ検出器を適用する」)により、
     ネストした候補の検出は既にこの段階に含まれていた。C案ではこの点を
     明確化するのみで、[3]自体の役割は変わらない。
     出力: ContentBlock候補のリスト(範囲・暫定blockKind・検出根拠)。
     ネスト候補・境界候補(番号・記号・ラベル等)を含む。

[4] Source Segmentation ── 責務を再定義(縮小)
     旧来は「候補を実際に子Sourceとして確定するか」まで判定していたが、
     C案では次の2つに責務を限定する。
     (a) 機械的に自明な確定: F3(既にトップレベルSourceと同じ階層構造上に
         ある)候補は、そのままStage1 Sourceとして確定する(既存のC1・C4
         ケース)。F5(内容が実質的に空)の候補は、確定候補にせず除外する
         (D1の③)。
     (b) それ以外(非自明)の候補は、確定Sourceにせず「Source候補」として
         保持し、F群の事実(2節)を付与して次段へ引き渡す。
     **「独立参照が必要かどうか」という意味判断(G群)は、この段階では
     一切行わない。**

[5] Faithful Restoration ── 適用対象を拡張、順序関係を再整理(3-3参照)
     確定Source・Source候補の両方に対して、可能な範囲で
     extractionRaw→sourceFaithfulの復元を試みる。復元の安定性(F4)は
     ここで判明し、[4]が保持するSource候補の事実へフィードバックされる。

[6] Parsing ── 変更なし(適用対象が確定Source・Source候補の両方に広がる点のみ)
     sourceFaithful→parsedの生成。

[7] Validation / Diagnostics ── 責務を拡張
     既存の構造整合性検証(gateChecks)に加えて、**「Source候補一覧+F群の
     事実」を、Parserの正式な出力物として確定させ、次段へ引き渡す責務**が
     加わる。候補一覧自体の構造的完全性(候補ごとにF群の事実が漏れなく
     付与されているか等)はgateChecksの検証対象になりうるが、候補の
     必要性判断そのものはここでも行わない。

  ═══════════════ Parserの責務範囲、ここまで ═══════════════

[8] 候補確定フェーズ(Parserの外側、新設) ── 人間レビュー / Derived Knowledge層
     [7]が出力したSource候補+F群の事実を入力として、G群の判断(独立参照
     必要性の最終確定)を行う。判断の結果、候補は「確定Source(親子構造を
     持つ正式なContentBlockとして生成)」または「確定不要(棄却、Source候補
     のまま記録のみ残すか破棄するかは別途検討)」のいずれかになる。
```

### 1-2. 個別の問いへの回答

- **旧Stage3-A相当(ネスト候補検出+構造的事実収集)はどこに属するか**:
  単一のStageにきれいには収まらない。**候補の検出そのものは[3] Block
  Detection**が担い、**F群の事実の集約・確定/非確定への振り分けは[4]
  Source Segmentation**が担う、という2段階にまたがる役割分担になる。
- **Source Segmentationは何を機械的に確定してよいか**: F3(既にトップ
  レベル)による確定と、F5(内容が空)による除外の**2種類のみ**。F2
  (教材明示境界の存在)やF8(反復先定義候補の存在)は、候補のメタデータ
  として記録するが、これらを理由に自動的に子Source化してよいわけでは
  ない(D3・206ページの反例が示すとおり、F2とF8が矛盾する場合がある)。
- **「子Source化が必要か」という意味判断をどこへ引き渡すか**: [7]の出力
  (Source候補+F群の事実)を経由して、Parserパイプラインの外側にある
  [8]候補確定フェーズ(人間レビュー/DK層)へ引き渡す。
- **Faithful Restorationとの前後関係**: 確定Sourceについては従来どおり
  [4]→[5]の順序で問題ない。Source候補については、[4]が提示する境界は
  **暫定的なもの**であり、[5]の復元結果によって候補の見え方(1つの候補か
  複数の候補か)が変わりうる(C3型)。この場合、[4]→[5]→[6]→[7]は
  一方向の直列パイプラインではなく、**復元が不安定な候補について[4]相当の
  候補パッケージングをやり直す反復的な関係**として扱う必要がある。これは
  既存の申し送り(`child_source_necessity_validation.md`12節)そのままの
  課題だが、**C案の下では深刻度が下がる**(3-3節で後述)。
- **Validation/gateChecksはどこで何を検証するか**: 引き続き[7]で、生成
  済みデータの構造・整合性を検証する(既存の位置づけを維持)。加えて、
  候補一覧という新しい出力物についても、「候補ごとにF群の事実が漏れなく
  付与されているか」等の構造的完全性チェックの対象になりうる。ただし
  「この候補は子Source化すべきか」という意味判断は、既存どおりgateChecksの
  対象にしない。

### 1-3. C案がSource Segmentation⇔Faithful Restorationの順序問題に与える影響

既存の申し送り(候補の判定自体が復元結果に依存する、C3型)は、C案でも
完全には解消しない。しかし、**現行案(Parserが最終確定まで行う)では、
順序が乱れると「確定してしまった子Source構造」を後から覆す必要があり
コストが高かった**のに対し、**C案では[4]の出力が最初から「暫定候補」で
あるため、[5]の復元結果が変わっても、破棄すべきは「確定済みの構造」では
なく「まだ確定していない候補リスト」で済む**。これはC案が既存の順序問題を
解決するわけではないが、**問題が生じた場合の訂正コストを下げる**という
効果がある。

## 2. Parserの出力契約(概念レベル)

C案では、Parserの出力は「確定Source群」と「Source候補群」の2種類に分かれる。
フィールド名・型の確定は行わず、**どの種類の情報が必要かという概念レベル**
で整理する。

### 2-1. 確定Source(既存のContentBlock/StructureNodeと同じ)

既存の4概念モデル(`extractionRaw`/`sourceFaithful`/`parsed`/`diag`)、
既存の`provenance`(該当する場合)をそのまま持つ。C案による変更はない。

### 2-2. Source候補(新しい出力契約、候補ごとに必要な情報)

| 情報の種類 | 内容 | 対応するF/G群 |
|---|---|---|
| 候補の範囲 | どのテキスト範囲を指すか(既存`location`相当) | - |
| 親候補/親Source | このネスト候補がどの確定Source(または他の候補)の内部にあるか | F3 |
| 境界の有無・種類(boundary type) | なし/番号/脚注記号/丸数字列挙/役割ラベル等。open vocabulary | F2 |
| 検出されたパターン種別 | 仕訳型/計算式/方程式等、暫定blockKind | F1 |
| 内部ネスト候補の有無 | この候補のさらに内部に、別のパターン候補が検出されているか | F6 |
| 内容の有無 | 候補範囲が実質的に空かどうか | F5 |
| 同型パターンの存在 | 構造的に類似した候補が他箇所にも検出されているか(一次スクリーニング) | F7 |
| 対応する抽象定義ブロック候補 | ラベルなし・topic直下等の位置に、同種のパターン候補が別途存在するか(存在の有無のみ。対応付けの確証は含まない) | F8 |
| Faithful Restorationの状態 | 復元が完了しているか、既知artifactが未解決のまま残っているか | F4 |
| diag / artifact | 既存の4-7節artifact構造(`kind`/`stage`/`resolved`/`note`相当) | F4 |
| 関連候補への参照(未確定) | 構造的に類似した別表現(D2の要約表等)が存在する場合、その参照。**ただし関係の性質(親子か、並列か)は今回確定しない**(7節) | G5(未確定のまま記録) |

**この出力契約の設計意図**: 各行は、いずれも1節2-1節の「Parserが事実として
確定できるもの(F群)」に対応しており、**独立参照必要性そのもの(G群)を
表すフィールドは意図的に含まない**。候補確定フェーズ([8])は、これらの
事実を読んで独自にG群の判断を行う。

## 3. 「確定Source」と「Source候補」の分離設計

### 3-1. 検討した3案

**案1: 候補も即座にContentBlockとして生成し、statusフィールドで区別する**

候補を検出した時点で暫定ContentBlockを生成し、`confirmationStatus:
"candidate" | "confirmed"`のようなフィールドで区別する。

- 利点: 既存のContentBlock構造をそのまま使い回せる。実装が単純。
- 欠点: 「まだ確定していないもの」をContentBlockという実体として生成
  してしまうと、ID発行・`sourceRefs`からの参照可能性等の副作用が生じる。
  CLAUDE.md原則4(推測しない、unknown/unresolvedとして保存する)、および
  既存設計(「親子Sourceは必要な場合だけ生成する条件付き機構」)の思想と
  やや整合しにくい——**確定していないものを、確定したものと同じ実体
  として扱ってしまう**。

**案2: 候補専用の軽量な別データ構造(Candidate/PendingSource等)を新設する**

候補を確定Sourceとは別の型として保持し、[8]で確定した時点で初めて
ContentBlockとして正式生成する。

- 利点: 「確定したものだけがContentBlockである」という既存モデルの純粋性
  を保てる。ID発行等の副作用も、確定した候補にのみ発生する。
- 欠点: 新しいデータ型を追加することになり、「新しいデータモデルを増やす
  前提としない」というユーザーの比較条件に最も反する。

**案3: 候補はContentBlockを生成せず、Parserの出力レポート(候補一覧)として
別管理する**

候補そのものを独立したエンティティとして生成せず、[7]が出力する「候補
一覧」という、Source/Derived Knowledgeデータとは別管理の出力物として
記録する。実際にContentBlockを生成するのは、[8]で確定した後(既存の
親子Source生成タイミングと同じ)。

- 利点: **既存のContentBlock/StructureNodeモデルを一切変更しない。**
  候補一覧という出力物は、既存の`gatechecks_invariant_validation.md`が
  既に確立した「gateChecksの結果はSource/Derived Knowledgeデータとは
  別の『Validation実行レポート』として持つ」という前例と構造的に一貫
  する(候補一覧も同種の「Parser成果物だが、Source本体とは別管理の
  レポート」として位置づけられる)。
- 欠点: 候補一覧という出力物自体の構造設計(2節の情報をどうまとめるか)
  は新規に必要になる。ただしこれは「Source/Derived Knowledgeスキーマの
  変更」ではなく、「Parserの出力レポート形式の設計」であり、既存の
  Validation実行レポート(6-3節、10節で未決事項として既に認識されている)
  と統合して扱える可能性が高い。

### 3-2. 比較・評価

| 観点 | 案1(statusフィールド) | 案2(専用データ型) | 案3(候補一覧レポート) |
|---|---|---|---|
| 既存モデルへの影響 | 小(フィールド追加のみ) | 大(新しい型の導入) | **なし**(ContentBlock/StructureNodeは無変更) |
| 設計思想との整合性 | やや低い(未確定のものを確定した実体として扱う) | 中 | **高い**(既存のValidation実行レポートの前例と一貫) |
| 実装の単純さ | 高い | 中 | 中(候補一覧の構造設計が別途必要) |
| ユーザー比較条件(既存モデル維持) | 部分的に満たす | 満たさない | **最もよく満たす** |

**この検討の結論(採用の可否ではなく、比較の結果として)**: 案3が、既存
モデルの維持・既存の設計思想(gateChecksの結果の別管理という前例)との
整合性の両面で最も無理がないと考えられる。ただし正式な採用判断は、候補
一覧レポートの具体的な構造設計(未着手)を経てから行うべきであり、今回は
比較の提示に留める。

## 4. 13ケースを新しいParserパイプラインへ通した確認

「入力→Structure/Block Detection→Source Segmentation→候補検出→Parser
出力→後段への引き渡し」という流れを13ケース全てに当てはめた。B1・B2・
C1・C4・D4は既存分析(`stage3_responsibility_reconsideration.md`5節)の
とおりF群のみで確定Sourceに到達し、候補確定フェーズへの引き渡しが発生
しない(以下では詳細確認を求められたA1・A2・C2・C3・D1・D2・D3のみ詳述
する)。

### 4-1. A1(定額法の設例内適用)

```
[3] 検出: 定義式候補(topic直下、境界なし)+ 各設例内の計算行候補(F1・F6)
[4] Segmentation: 定義式→F3(トップレベル)により確定Source化。
                  計算行→F3=偽(親設例の内部)、F2=なし、F8=真(定義式が
                  topic直下に存在)→Source候補としてパッケージング
[7] Parser出力: 確定Source(定義式)+ Source候補(計算行、F1・F6・F8=真)
[8] 後段判断: F8を手がかりに「定義の適用である」と判断し子Source化を確定
```
**自動確定できる範囲**: 定義式自体の確定Source化、および計算行が「候補で
あること」まで。**確定しない範囲**: 計算行を実際に子Source化するかどうか。

### 4-2. A2(固定資産買換※1〜※5)

```
[3] 検出: `※N`という境界候補(F2)+ 各脚注内の算定式候補(F1)
[4] Segmentation: F3=偽(ボックス内部)、F2=真(明示境界)
                  →Source候補としてパッケージング(境界ごとに分離)
[7] Parser出力: Source候補×5(いずれもF2=真)
[8] 後段判断: 各脚注の内容を評価し確定する
```
**自動確定できる範囲**: 境界(`※N`)の存在・位置に基づく候補への分離まで。
**確定しない範囲**: 各脚注を実際に独立Sourceとして確定するかどうか。**F2が
真であることは、確定の根拠として直接使わない**(D1の②③、D3・206ページの
反例により、明示境界の存在だけでは確定できないことが分かっているため)。

### 4-3. C2(差額補充法反復計算)

```
[3] 検出: 具体数値の計算式候補×4(F1)
[4] Segmentation: F3=偽、F2=なし、F8=偽(反復先の抽象定義候補が存在しない)
                  →Source候補としてパッケージング
[7] Parser出力: Source候補×4(F8=偽という事実付き)
[8] 後段判断: 「型の反復」か「独立した4つの具体例」かを判断する
```
**自動確定できる範囲**: 候補の存在と、F8=偽という事実の記録まで。**確定
しない範囲**: 独立参照の要否そのもの。F8=偽という事実だけでは必要/不要
のどちらにも収束せず、**完全に[8]側の判断に委ねられる**——C案が最も
明確に効果を発揮するケース。

### 4-4. C3(複数行分断式)

```
[3] 検出: 単一行ベースの検出器では、分断された式が複数候補であるかのように
          誤検出されうる
[4] Segmentation: F4=偽(Faithful Restoration未解決)
                  →候補のパッケージング自体を保留
[5]→[4] ループ: 復元が安定した時点で候補パッケージングをやり直す
[7] Parser出力: 復元完了後に初めてSource候補として確定的に出力される
[8] 後段判断: 復元完了後の候補に対して行う
```
**自動確定できる範囲**: F4=偽であるという事実の検出と、それに基づく
「候補確定の保留」まで。**確定しない範囲**: 候補の境界・個数そのもの(復元
未完了のため)。**C案でもF4=偽の場合はStage3-A相当の候補検出自体が完了
できず、候補確定フェーズに渡す以前の問題として扱われる**——既存の責務
分離(Faithful Restoration完了が前提)とC案が矛盾しないことを示す実例。

### 4-5. D1(①②③、①内部の式)

```
[3] 検出: ①②③という境界候補(F2)。①の内部にのみ長文式候補(F1・F6)。
          ②は説明文のみ(内部候補なし)。③はF5=空。
[4] Segmentation: ①②③という境界自体はStructureNode/ContentBlockの通常の
                  階層として確定Source化してよい(教材構造そのものであり、
                  候補ではなく既存の階層認識の範囲)。
                  ②・③→F1(内部候補)が存在しないため、そもそも候補が
                  生成されない(G群の判断すら発生しない)。
                  ①内部の式→F6により候補としてパッケージング。
[7] Parser出力: 確定Source(①②③の境界構造)+ Source候補(①内部の式のみ)
[8] 後段判断: ①内部の式についてのみ、A1と同型の判断が必要。②③は判断対象
              にすらならない
```
**自動確定できる範囲**: ②③に候補が存在しないことの確定(F1不在による
機械的な除外)まで。**確定しない範囲**: ①内部の式の独立参照要否のみ。
**D1は、F群だけで「そもそも候補にすべきかどうか」まで絞り込める好例で
あり、[8]側の負荷を減らす効果を示している。**

### 4-6. D2(振出人/名宛人/指図人)

```
[3] 検出: 役割ラベル境界候補(既知語彙になければ検出器の追加が前提)+
          各仕訳候補(F1)+ 末尾の要約表現(構造的類似、F7相当)
[4] Segmentation: F3=偽(➋為替手形の内部)、境界形式=ラベル(F2相当の
                  新語彙として記録)→Source候補としてパッケージング
[7] Parser出力: Source候補×3(ラベル境界+F1)+「末尾に構造的に類似した
                表現が存在する」という関連メモ(関係性は未確定のまま記録)
[8] 後段判断: 各仕訳の独立参照必要性、および要約表との関係性(G5)の両方を
              判断する
```
**自動確定できる範囲**: 3つの仕訳候補の存在と、末尾表現との構造的類似の
検出まで。**確定しない範囲**: 各仕訳の独立参照要否、および**要約表との
関係性の構造化そのもの**(これは7節で明示的に未決事項とする)。

### 4-7. D3(147/149ページ・206ページ)

```
147/149:
[3] 検出: 定義式候補(`(N)`境界、F2)+ 適用計算候補(`※`境界、F2)
[4] Segmentation: F2=真(複数レベルで一致)、F8=真(定義候補がp147に存在)
                  →Source候補としてパッケージング、F2・F8がともに真という
                  「一致した」事実の組み合わせを記録
[7] Parser出力: Source候補+F2=真・F8=真という事実
[8] 後段判断: F2・F8の一致により、比較的合意形成しやすいと期待される

206:
[3] 検出: 適用計算候補(`(N)`・`※`境界、F2=真)
[4] Segmentation: F2=真、F8=偽(抽象定義候補が教材上見当たらない)
                  →Source候補としてパッケージング、F2とF8が**矛盾する**
                  事実の組み合わせをそのまま記録
[7] Parser出力: Source候補+F2=真・F8=偽という、矛盾する事実
[8] 後段判断: 判断が割れる可能性が高いが、これは[8]側の課題であり、
              **Parser自身はこの矛盾を解消しようとしない**
```
**自動確定できる範囲**: 両ケースともF2・F8の値そのものの検出・記録まで。
**確定しない範囲**: 独立参照の要否。**206ページは、Parserが矛盾する事実を
無理に統合・裁定せず、そのまま候補確定フェーズへ引き渡すというC案の核心が
最も明確に表れるケース。**

## 5. C案による既存設計への影響

| 対象 | 分類 | 内容 |
|---|---|---|
| Stage1〜3 Source Segmentation | **設計変更が必要** | Stage2/3の「候補を子Source化する」という枠組み自体を、「候補の検出・パッケージングまで」に narrows する。Stage1(視覚的完結単位)はF3で機械的に確定できる範囲と一致し、位置づけは維持される |
| 親子Source | **記述だけ変更でよい可能性が高い** | 「条件付き機構」という思想自体は維持できるが、確定のタイミングが「Parserが候補検出時点で提示」から「[8]候補確定フェーズが確定した時点で正式生成」に変わる。`parentBlockId`等のデータモデル自体は変更不要 |
| provenance | **そのまま維持できる** | 確定Sourceに対して適用される限り、既存の`diag`外配置・open vocabulary設計は変更不要。候補段階でのprovenanceの扱いは3節の案(1/2/3)次第だが、案3を採用すれば候補はそもそもprovenanceを持たない(候補一覧側の情報として扱う)ため影響なし |
| relation | **そのまま維持できる(ただし7節の論点を除く)** | 既存2語彙(`extracted_from_parent`/`footnote_of_parent`)は確定Source間の関係を表すものであり、C案による責務再定義の影響を受けない。D2の新しい関係(本文-要約表)は独立した論点として7節へ切り出す |
| sourceFaithful重複 | **そのまま維持できる** | 既存方針(重複許容+`provenance`)は確定Source同士の関係を扱うものであり、候補段階の話ではないため無変更 |
| Parser / Derived Knowledge責務境界 | **設計変更が必要(ただし既存原則の拡張)** | 既存4節は「role割り当て・Knowledge同一性判定」をDK層としていたが、C案では「候補を確定Sourceにするかどうかの判断」自体もDK層/人間レビュー側の責務として明示的に追加される。既存原則と矛盾はしないが、適用範囲が明確化・拡張される |
| gateChecks | **記述だけ変更すればよい可能性が高い** | 既存の位置づけ(意味判断器ではなく構造・整合性の検証)は変わらない。検証対象に「候補一覧の構造的完全性」が加わる可能性があるが、既存のA/B/C分類の枠組みでそのまま扱える |
| diag | **一部要検討** | F4(Faithful Restoration状態)は既存の`diag.extraction.artifacts`で表現済みのため無変更。ただし候補が持つF群の事実全体を`diag`に載せるか、案3の「候補一覧」側に載せるかは、3節の結論次第で変わるため、完全に「維持」とは言い切れない |
| sourceRefs.role | **そのまま維持できる** | DK層が確定Sourceに対して付与するという既存の性質・タイミングに影響しない。むしろ「Parser側はrole割り当てを行わない」という既存原則がより一貫して守られるようになる |

## 6. D2「本文個別仕訳と要約表」のrelation問題(明示的に未決事項へ)

`stage3_additional_validation.md`(D2、77ページ)・`stage3_responsibility_
reconsideration.md`4節で確認したとおり、本文中の個別仕訳(振出人/名宛人/
指図人)と、ページ末尾の要約表現との関係は、既存の`relation`語彙
(`extracted_from_parent`/`footnote_of_parent`、いずれも1対1の親子関係を
前提)では表現しきれない可能性がある(多対1、かつ親子ではなく並列した表現
同士の関係である可能性)。

**今回のパイプライン再定義においても、この論点には結論を出さない。**
2節の出力契約では「関連候補への参照(未確定)」という形で、関係の**存在**
だけは記録できるようにしたが、関係の**性質**(親子か・並列か・どちらの
relationにも該当しない第3の概念が必要か)は今回判断していない。

ユーザー指示どおり、以下には進んでいない。

- 既存relation語彙で表現できるかどうかの最終判断
- 新しいrelation語彙の追加
- 多対多関係モデルの導入

**「C案を採用しても残る、独立したデータモデル論点」として明示的に未決事項
に残す。**

## 7. C案を正式採用できる段階か

**評価: もう1回だけ小規模検証が必要。**

今回の整理により、C案自体に**新しい深刻な問題は見つからなかった**。
むしろ、13ケース全てに新パイプラインを通した結果(4節)、F群だけで完結する
ケース(B1・B2・C1・C4・D4)と、G群の判断を[8]へ引き渡す必要があるケース
(A1・A2・C2・C3・D1・D2・D3)が明確に切り分けられ、既存の順序問題(3-3節)
の深刻度もC案の下で下がることが確認できた。

ただし、正式採用の前に確認すべき具体的な論点が残っている。

1. **3節の「確定/候補分離」3案のうち、どれを採用するかがまだ決まって
   いない。** 案3(候補一覧レポート、既存モデル無変更)が比較上は最も
   有力だが、これは机上の比較にとどまり、実際にF群の事実一式(2節)を
   候補一覧としてまとめてみたときに、無理なく機能するかは未確認。
2. **候補確定フェーズ([8])の受け皿が全く未設計。** 人間レビューに候補+
   F群の事実をどう提示するか、DK層の統合判断プロセスがどこまでこれを
   引き受けられるかは、今回一切検討していない(ユーザー指示どおり、
   意図的にスコープ外とした)。
3. **[4]⇔[5]の反復関係(3-3節、C3型のループ)が、実装レベルで破綻なく
   回るかが未検証。** 今回は概念レベルで「深刻度が下がる」と評価した
   のみで、実際に小規模スクリプトで往復させてみた確認はしていない。
4. **7節のrelation問題は意図的に未解決のまま。** これがC案採用の障害には
   ならないと考えられる(候補の存在自体は記録できるため)が、次フェーズで
   放置し続けられる論点ではない。

**追加検証で確認すべきこと(次にもし小規模検証を行うなら)**:

- 3節の案3(候補一覧レポート)を、A1・A2・C2・D1・D2のような実際の候補
  群に対して試作し、2節の出力契約(各情報項目)で過不足なく表現できるかを
  確認する。
- C3型のケース(復元不安定)に対して、[4]→[5]→[4]という往復を模擬的に
  行い、候補パッケージングのやり直しが自然に回るかを確認する。
- (候補確定フェーズの詳細設計そのものではなく、あくまで)Parser側の出力が
  人間レビューにとって過不足ない情報量になっているかを、13ケースのうち
  数件を使って簡易的に確認する。

これらが確認できれば、C案を正式採用してParser設計の改訂(`parser_design_
proposal.md`の書き換え)に進める段階に達すると考えられる。
